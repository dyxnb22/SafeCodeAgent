## 评估前言：Gemini 扫描报告的校正

Gemini 3.1 的扫描报告抓住了若干真实问题，但也有几处需要校正：

| 条目 | 校正 |
|------|------|
| IDE Plugin / Web UI | **非目标**。项目 CLAUDE.md 明确"terminal-only by design"，不应该做 VS Code 扩展或 Web 界面 |
| DAG 并发子代理 | **被高估**。LangGraph 式并发调度会引入非确定性，与 checkpoint/audit 链冲突；现有 SubagentPool 已是够用的并发边界 |
| Embedding 向量搜索 | **已部分实现**（`safecode-agent[semantic]` optional extra）；差的是召回质量，不是完全缺失 |
| 同步 urllib | **部分真实**，但已有重试机制（`retry.py`）；核心问题是无 streaming backpressure，不是纯同步问题 |
| 过胖 AgentLoop | **完全真实**，1603 行 / 29 个方法，混合了 dispatch、budget、journal、recovery、MCP 路由 |
| 状态管理脆弱 | **完全真实**，resume 通过 journal events 硬凑，单 `session.json` 没有版本化的 checkpoint 入口 |

此外，Gemini 漏掉了以下第一手发现：

1. **mock 路径 vs native-tool 路径的覆盖断层** — mock provider 走 `AgentToolIntentResponse` 旧 schema，native-tool 路径只有 OpenAI/Anthropic 走；6000+ 测试中最关键的 agentic 路径用 mock 覆盖，真实行为只靠 live eval 抓到。
2. **eval 100% 可疑** — 28 个 inline fixtures 全过，11 个 SWE-bench 风格 fixtures 全过；所有 fixtures 都是 1-turn 解决，没有测多轮推理场景。
3. **search_symbol 孤岛** — v6.25 加了 `search_symbol` native tool，但 context collector 不会主动在 prompt 里提示模型"你可以用 search_symbol 找符号"；工具存在但发现率低。
4. **ConversationBuffer 阈值硬编码** — turn_count > 12 触发压缩，不可配置，不随 model context window 动态调整。
5. **validation/repair 仅支持 pytest** — `ValidationLoop` 的 run_command 只支持 pytest-like 工具；LSP diagnostics 与 repair 的闭环在代码里是浅层胶水，没有按错误类型做精准文件召回。

## v6.29 — AgentLoop 分层重构

### 问题

`src/safecode/agent/loop.py` 是 1603 行 / 29 个方法的上帝类，混合了：
- 会话生命周期管理（start / resume / abort）
- 计划执行和步进（step / native_step / run）
- 工具路由（MCP、subagent、patch、write tools）
- 预算追踪和卡死检测
- journal 写入和 typed-step 记录
- 上下文压缩和 session memory

**后果**：每次加功能都要在这个类里找到正确位置，且任何 bug 的影响范围难以预判。

### 方案

不删功能，只拆边界。拆成 4 个协作模块：

```
agent/
  loop.py              ← 只保留 AgentLoop 主类壳 (~200 行)
  loop_planner.py      ← _plan_steps / _start_planned_session / dynamic replan
  loop_dispatcher.py   ← _build_dispatcher / _execute_*_step 各类工具路由
  loop_budget.py       ← _abort_if_stuck / _record_budget_failure / cost tracking
  loop_journal.py      ← _classify_and_record / _record_step_journal_entry
```

`AgentLoop` 本身变成协调者（Orchestrator pattern），各模块单独可测。

### 验收

- 所有现有测试绿（行为不变）
- `loop.py` 降到 ≤400 行
- 每个子模块独立 import 不引入循环依赖
- 新增 `test_loop_planner.py` 单测 plan 逻辑

## v6.30 — 跨 Session 工程记忆 (Workspace Memory Store)

### 问题

现有 `MemoryFacade` 只存人工写入的 project notes 和 recent failures，不会自动学习：
- "这个项目跑测试的命令是 `uv run pytest`"
- "上次修 parse_config 时发现 None 需要特判"
- "这个 codebase 的命名习惯是 snake_case，不是 camelCase"

每次新会话 agent 从零开始，无法利用跨 session 积累的经验。

### 方案

新增 `WorkspaceMemoryStore`（写入 `.sac/workspace_memory.jsonl`）：

```python
@dataclass
class WorkspaceMemoryEntry:
    key: str          # 语义键，如 "test_command" / "naming_convention" / "bug:parse_config"
    value: str        # 经验内容
    source: str       # "agent_observed" | "user_stated" | "inferred_from_history"
    confidence: float # 0.0–1.0
    timestamp: str
    session_id: str
    evictions: int    # 被覆盖/更新次数
```

**自动写入时机**：
1. `apply()` 成功后，agent 总结"这次改了什么、为什么"写入 key=`fix:<file_stem>`
2. `run_command` 成功后，写入 key=`build_command` / `test_command`  
3. 会话结束时（`/commit` 或 `exit`），写入 key=`session_summary:<date>`

**注入时机**：  
`ContextCollector.collect()` 在构建 prompt 前，加载最相关的 top-5 workspace memory entries（按 key 语义相关度排序）。

**安全约束**：
- `value` 写入前 `redact_secrets()`
- 单条 value ≤ 2000 chars
- 总文件 ≤ 500KB（超限 LRU eviction）
- `source=agent_observed` 不可被 project-local config override

### 验收

```bash
# session 1
sac shell → "fix parse_config handling None in src/config.py" → apply
# session 2（全新 shell）
sac shell → "add tests for parse_config"
# agent prompt 里自动包含：
# [workspace memory] fix:config — parse_config returns {} for None/empty (observed 2026-06-17)
```

## v6.31 — 多轮推理 Eval Fixtures（诚实的 multi-turn 数字）

### 问题

所有现有 28 + 11 = 39 个 fixtures 都是 1-turn 解决。真实用户场景是：
- 第 1 轮：找到 bug 但 patch 不对
- 第 2-3 轮：根据测试反馈修正
- 第 4 轮：边界情况修复

这导致 100% 通过率在简历上看起来像 cherry-picked，而不是真实评测。

### 方案

新增 8 个多轮 fixtures，每个都设计为"正确 fix 需要 ≥2 轮交互"：

| Fixture | 多轮场景 | 预期 turns |
|---------|---------|-----------|
| `multi-turn-wrong-import` | 第 1 轮修了函数但 import path 错，第 2 轮修 import | 2-3 |
| `multi-turn-partial-rename` | rename 了定义但漏了 2 个 call site | 2-3 |
| `multi-turn-type-error-chain` | 修了一个类型错误暴露另一个 | 3-4 |
| `multi-turn-test-driven` | 先补测试，再修实现，再确认 | 3-4 |
| `multi-turn-config-cascade` | 改了 schema 需要同步改 default + validator | 3-5 |
| `multi-turn-import-cycle` | 引入 circular import，需要重构 | 4-6 |
| `multi-turn-async-sync-mismatch` | async/sync 边界错误，全链路受影响 | 4-6 |
| `multi-turn-regression-guard` | 修了 bug 破坏了另一个测试 | 3-5 |

每个 fixture 的 `success_condition` 要运行完整 pytest，不接受"只修了文件内容"。

**期望结果**：pass_rate 在 50-80% 之间（不再是 100%），这才是诚实的评测数字。

### 验收

```
Multi-turn eval results (DeepSeek v4-flash):
  6/8 passed (75%)  avg 3.2 turns  avg 8400 tokens
```

## v6.32 — 动态 Re-planning

### 问题

当前 plan 是"一维数组"，执行到 step N 如果失败，只能：
1. 继续下一步（忽略失败）
2. stop for user（交还控制权）

没有"我之前的方案不对，让我换个思路"的能力。实际上这正是大量 SWE-bench 失败的原因：agent 发现 patch 验证失败，但已经没有新的 plan step 可以执行。

### 方案

在 `AgentLoop` 中引入 `_try_replan()` 钩子：

```python
def _try_replan(self, state: AgentSessionState, failure_reason: str) -> bool:
    """
    When validation fails N times on the same file, discard current plan
    and generate a new one with the failure context injected.
    Returns True if replan succeeded, False if we should stop for user.
    """
```

触发条件（全部满足才触发，避免滥用）：
1. `repair_attempts >= 2`（已重试过至少两次）
2. `failure_category in (validation_fail, patch_parse_fail, loop_stuck)`
3. `replan_count < 2`（最多 replan 两次，防止无限循环）
4. `full_auto` 模式（建议模式仍 stop for user）

Replan 的 prompt 注入：
- 原始 goal
- 已尝试的方案摘要（从 journal 提取）
- 失败原因（diagnostics）
- 明确指令："原方案失败，请重新规划，避免使用同一思路"

### 验收

```
# 故意设计一个会先生成错误 patch 的 fixture
multi-turn-replan-required:
  turn 1: wrong patch → test fails
  turn 2: repair also fails  
  replan triggered → new plan → correct patch
  success: true
  replan_count: 1
```

## v6.33 — Context Back-pressure（模型窗口感知）

### 问题

当前上下文截断策略：
- 文件内容：固定 400 行
- 会话压缩：固定 12 轮后触发 LLM 摘要
- 工具结果：固定 8000 chars/条

**不感知模型的实际 context window**。DeepSeek 是 64k，Claude Sonnet 是 200k — 用同一个 budget 处理两者是浪费（Claude 可以放更多上下文）或危险（小模型溢出）。

### 方案

新增 `ModelContextProfile`（从 provider config 读取或从模型名称推断）：

```python
@dataclass
class ModelContextProfile:
    model_id: str
    context_window_tokens: int          # e.g. 64000 for deepseek-chat
    safe_input_ratio: float = 0.70      # 最多用 70% 给 context
    compact_threshold_ratio: float = 0.60  # 60% 时触发压缩

    @property
    def safe_input_tokens(self) -> int:
        return int(self.context_window_tokens * self.safe_input_ratio)
```

`ContextBudgetManager` 从 `ModelContextProfile` 读取上限，动态计算每种 context 类型的 token 配额：

```
total_safe = 44800  (70% of 64k)
- system prompt:   4000
- task context:    8000  
- selected files: 20000  
- tool results:    8000
- conversation:    4800
```

当任何类型超出配额时，向 `ContextCollector` 发送 backpressure signal，触发该类型的压缩（而非整体截断）。

### 验收

- `sac doctor --live` 显示 `context_budget: 44800/64000 tokens (70% cap)`
- 长会话不再出现 `context length exceeded` 错误
- claude-sonnet 配置下自动使用更大的 context 窗口

## v6.34 — Native-tool Mock 覆盖补齐

### 问题（代码层面发现）

`MockLLMClient` 没有 `choose_tool_native()` 方法，所以所有 6000+ 测试走的是老 JSON schema 路径（`AgentToolIntentResponse`），而真实 provider（Claude、OpenAI、DeepSeek）走 native tool 路径。

这意味着：
- native_step 路径几乎没有 mock 覆盖
- 在 `_build_dispatcher` 注册的 search_symbol、edit_file、run_command 等工具，在现有 CI 中从未被端到端调用
- live eval 中测到的是真实行为，但 CI 测不到

### 方案

```python
class MockNativeToolLLMClient(MockLLMClient):
    """Mock LLM client that responds via native tool calls (v6.34)."""
    
    def __init__(self, scripted_calls: list[NativeToolCall]):
        self._scripted_calls = list(scripted_calls)
        self._step_index = 0
    
    def choose_tool_native(
        self, goal: str, context: dict, specs: list[NativeToolSpec],
        *, conversation_history=None
    ) -> AgentNativeToolCallResponse | AgentStopForUserResponse:
        if self._step_index >= len(self._scripted_calls):
            return AgentStopForUserResponse(message="scripted sequence exhausted")
        call = self._scripted_calls[self._step_index]
        self._step_index += 1
        return AgentNativeToolCallResponse(tool_calls=[call])
```

新增 `tests/test_native_tool_loop.py`：端到端测试 `read_file → edit_file → run_command → stop` 序列，全程走 native tool path，不碰 live API。

### 验收

- `PYTHONPATH=src pytest tests/test_native_tool_loop.py -q` 全绿
- 覆盖：read_file 路径、edit_file 路径（checkpoint 验证）、run_command 路径、stop 路径

## v6.35 — search_symbol 发现率提升

### 问题

`search_symbol` 作为 native tool 已注册，但：
1. Agent prompt 里没有明确提到这个工具的用途
2. Context selector 没有在"符号找不到时"主动建议使用它
3. `find_references` (Jedi) 和 `search_symbol` (ripgrep) 功能重叠但 prompt 里没有说明区别

### 方案

1. **Prompt 更新**（`src/safecode/agent/prompts.py`）：
   ```
   - search_symbol(name, kind?) — find where a symbol is defined across all project files
     Use this FIRST when you don't know which file contains a definition.
     Prefer over grep_files for finding function/class definitions.
   - find_references(name) — find Python import + call sites (requires jedi, Python only)
     Use after search_symbol to find all usages.
   ```

2. **Context collector hint**：当 `query` 包含 "where is" / "find" / "定义" 等词时，注入 `context["tool_hint"] = "search_symbol"` 提示。

3. **Ambiguity resolution**：当 `find_references` 返回 ambiguous 时，自动降级到 `search_symbol` 作为 fallback。

### 验收

- eval fixture `swe-multifile-symbol-find`：goal 只说"find and rename X"，不说文件路径 → agent 自主用 search_symbol 定位 → 成功
- 新增 `tests/test_search_symbol_prompt_hint.py`

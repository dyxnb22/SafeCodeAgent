# v4.9 AI Shell MVP Roadmap

Status: planning. No runtime behavior change in this document.
Baseline: tag `v4.8.2`, with the v4.1-v4.8 shell-first train complete.
Authoring date: 2026-06-04.

## Goal

Make SafeCode Agent usable as a local AI shell:

- User can `cd` into a target project.
- User can start one command, expected as `sac shell`.
- User can ask natural-language questions about the project.
- The shell can build enough project context to explain structure, entrypoints,
  tests, stack, recent state, and relevant files.
- The shell can propose edits, run checks, apply approved patches, resume work,
  debug failures, and commit locally by reusing existing SafeCode surfaces.

The product target is a Claude Code-like local workflow, but with SafeCode's
existing safety posture: explicit proposals before mutation, approval-gated
apply/commit/run paths, checkpoints, rollback, audit, dirty-tree guard, and no
remote operation by default.

## Scope Decisions

This v4.9 plan intentionally ignores RAG and LangGraph. The next bottleneck is
not embeddings or an external graph runtime; it is the product loop that turns
the already-shipped primitives into one coherent AI shell.

In scope:

- `sac shell` as the unified interactive entrypoint.
- Lightweight shell session state and conversation history.
- Natural-language routing into existing SafeCode commands and services.
- Project overview/context assembly from local structured signals.
- Approval-gated edit/apply/run/commit orchestration.
- Deterministic mock-provider tests and optional advisory live-provider smoke.
- Documentation that teaches the AI shell workflow first.

Out of scope for v4.9:

- Vector databases, embeddings, or traditional RAG indexes.
- LangGraph or any external graph/orchestration runtime.
- Stable contract promotion for new v4.9 surfaces.
- IDE integration, remote execution, hosted service behavior, or git push/PR
  automation.
- Automatic patch application without explicit approval.

All new v4.9 user-facing surfaces remain EXPERIMENTAL unless a later contract
cut explicitly promotes them.

## Version Train

### v4.9.0 - Shell Session and REPL

Add the minimal interactive shell loop.

Deliverables:

- Register `sac shell` as an EXPERIMENTAL root command.
- Add a TTY-friendly REPL with deterministic non-TTY/script behavior.
- Support core slash commands such as `/status`, `/task`, `/overview`, `/apply`,
  `/commit`, `/debug`, `/help`, and `/exit`.
- Persist lightweight shell session state under `.sac/shell/` without changing
  stable public contracts.
- Attach shell turns to the current v4.1 task state and audit metadata.
- Keep all mutation paths approval-gated by delegating to existing SafeCode
  apply/commit/run behavior.

Validation focus:

- CLI registration/help surface.
- TTY and non-TTY shell behavior.
- Session persistence and corruption tolerance.
- Task/audit wiring.
- No auto-apply regression.

### v4.9.1 - Natural-Language Router

Turn ordinary user messages into shell actions while reusing existing command
substrates.

Deliverables:

- Implement an intent router for ask, edit, fix, run, status, apply, commit,
  debug, overview, and exit intents.
- Prefer structured internal calls over shelling out to command strings.
- Require explicit confirmation for write-class actions.
- Preserve profile-based test/lint/typecheck/build routing.
- Provide deterministic mock-provider coverage for multi-turn shell flows.
- Make ambiguous intent safe: ask a clarifying question or route to read-only
  `ask`, never directly mutate.

Validation focus:

- Intent classification matrix.
- Approval prompts for mutation/run/commit paths.
- Read-only questions remain read-only.
- Existing command exit-code semantics remain unchanged.

### v4.9.2 - Project Overview and Context Pack

Give the shell enough project understanding to answer "what is this project?"
and make useful edit proposals without adding RAG.

Deliverables:

- Add a structured project overview builder that combines existing signals:
  project profile, git status, detected stack, entrypoints, tests, docs,
  pinned memory, current task, recent failures, and high-signal file list.
- Expose the overview through `sac shell /overview` and use it as first-turn
  context for shell questions.
- Keep context bounded and deterministic; avoid embedding/vector storage.
- Redact secrets and respect existing safe-read/path policies.
- Add explainable context budgeting so skipped files/signals are visible in
  debug output.

Validation focus:

- Python/TypeScript/Go/Rust fixture repos.
- Bounded context behavior.
- Secret/path redaction.
- Overview determinism.
- Shell answers include project structure without requiring RAG.

### v4.9.3 - AI Shell Docs and Smoke

Cut the AI shell documentation and smoke coverage.

Deliverables:

- Add a shell-first tutorial centered on `cd project && sac shell`.
- Update README, MVP guide, troubleshooting, version matrix, public contracts,
  versioning policy, and current Claude skill context.
- Add `sac smoke ai-shell` or equivalent smoke coverage for the local shell
  loop using deterministic fixtures.
- Add optional live-provider smoke documentation, clearly advisory unless
  validated in CI or release evidence.
- Record that v4.9 adds no stable contracts and does not schedule v5.

Validation focus:

- Docs claims guard.
- Public-contract snapshots unchanged.
- Release preflight.
- Full suite after the train.

## Acceptance Criteria

By the end of v4.9.x, a user should be able to run:

```sh
cd /path/to/project
sac shell
```

Then ask:

- "What is this project?"
- "Find the likely bug in this failure."
- "Make the smallest safe fix."
- "Run the tests."
- "Apply the patch."
- "Commit this task."

The shell should maintain task continuity, explain what it is about to do,
request approval before mutation, run through existing SafeCode safety paths,
and leave recoverable state for resume/debug/rollback.

## Non-Goals

Do not implement RAG, embeddings, vector search, LangGraph, hosted agents, IDE
protocols, push/PR operations, or stable API promotions in v4.9.

## Suggested Implementation Order

1. Build the shell loop around existing primitives.
2. Add intent routing.
3. Add project overview/context assembly.
4. Cut docs and smoke tests.

This order is chosen because it gets the user-visible AI shell online before
optimizing deeper context assembly, while preserving the safety behavior that
already exists.

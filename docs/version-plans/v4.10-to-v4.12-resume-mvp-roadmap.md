Target completion: tag `v4.12.3` (resume-ready MVP cut).

### Revision 2026-06-05 (pre-implementation review)

The v4.11 train was originally written as if the agent runtime had to be
introduced from scratch. A pre-implementation review against the v4.9.3
codebase corrected four issues; the body below already reflects them:

1. **v4.11 evolves the existing `AgentLoop`, not a parallel `AgentTaskRunner`.**
   `src/safecode/agent/loop.py:58` already implements `AgentLoop` with
   `step()` / `run()` returning `AgentStepResult` / `AgentRunResult`, and
   `sac agent run` already exists at `src/safecode/cli_agent.py:156`. The
   v4.11 batches add a typed step/kind/status layer and a validation loop
   **on top of `AgentLoop`** rather than introducing a new orchestrator.
2. **Journal path is unified to the existing store.** The agent journal
   already lives at `.sac/agent_journals/<session_id>.jsonl` via
   `AgentJournalStore` (`src/safecode/state/journal.py:45`). v4.11.1
   extends this store with new event types instead of writing a second
   journal under `.sac/tasks/...`.
3. **Doctor's "no network" boundary is stated precisely.** `sac doctor`
   already performs a PyPI update check (`src/safecode/doctor.py:204`).
   v4.10.2 promises only that **doctor makes no provider network request**;
   the existing update check is gated by an offline-safe knob in the same
   batch.
4. **DeepSeek preset requires explicit `OpenAICompatibleLLMClient` work.**
   The current client reads only `OPENAI_API_KEY` / `SAFECODE_LLM_API_KEY`
   (`src/safecode/llm/openai_client.py:51`) and POSTs directly to
   `config.llm.base_url` (`src/safecode/llm/openai_client.py:149`). v4.10.0
   now lists the client-side changes — `api_key_env` resolution and
   `/v1/chat/completions` endpoint normalization — as required tasks, not
   only factory wiring.

## 1. Product Goal (Resume-Ready MVP)

> SafeCode Agent v4.12 demonstrates a **complete, reliable, safety-gated local
> AI coding workflow** driven by a real LLM provider, capable of going from
> a natural-language task to a tested, locally-committed change without ever
> bypassing diff review, checkpoint, audit, rollback, policy, or dirty-tree
> guard.

Concretely, after `v4.12.3` a recruiter or peer reviewer can:

1. `git clone safecode-agent && uv sync`
2. `export DEEPSEEK_API_KEY=...`
3. `sac setup --wizard` (pick `deepseek` preset)
4. `sac doctor` (confirms key, base URL, model, network policy)
5. `cd examples/fastapi-todo`
6. `sac agent run "add a DELETE /todos/{id} endpoint with a passing test"`
7. Review the proposed plan, the proposed patch, run the validation suite,
   approve, apply, and `sac commit` — all from one transcript.
8. Read `docs/tutorials/from-task-to-tested-commit.md` and reproduce the run
   from a recorded transcript bundled in the repo.

What this MVP **does not** try to be:

- A full Claude Code clone (no IDE, no remote, no cloud).
- A RAG / embedding / vector-DB system.
- A LangGraph or external orchestration runtime.
- A push/PR/CI automation surface.
- An auto-applying or auto-committing agent.

What this MVP **does** prove:

- Safety-first architecture composes into a real product loop.
- A real provider (DeepSeek) runs reliably enough for live demos with retry,
  timeout, and rate-limit handling.
- Existing SafeCode primitives are powerful enough that an agentic controller
  on top of them is a thin, reviewable layer — not a rewrite.

## 2. Target Architecture

The next stage adds **two new layers** above the existing safety runtime and
keeps every safety gate untouched.

```text
+----------------------------------------------------------------------+
|  UX layer                                                            |
|  - sac shell --agentic                                               |
|  - sac agent run "<goal>"                                            |
|  - Transcript renderer + demo script (examples/fastapi-todo)         |
+--------------------------------+-------------------------------------+
                                 |
                                 v
+----------------------------------------------------------------------+
|  Agentic Orchestration layer (EVOLVED FROM v4.9 AgentLoop)           |
|  - AgentLoop (src/safecode/agent/loop.py) gains typed step model:    |
|    AgentStep{kind, status, requires_approval, failure_category}      |
|  - Existing AgentJournalStore at .sac/agent_journals/<sid>.jsonl     |
|    learns new event types (step_kind, validation, repair, resume).   |
|    No second journal is introduced.                                  |
|  - StepBudget reuses v4.4 TaskBudget (already wired into AgentLoop). |
|  - HumanCheckpoint: existing PatchPendingAction / approval store     |
|    bindings are reused; v4.11.0 adds the per-kind hard rules.        |
|  - ValidationLoopController (new): drives run --suite test|lint|...  |
|  Calls EXISTING command surfaces; never reimplements them.           |
+--------------------------------+-------------------------------------+
                                 |
                                 v
+----------------------------------------------------------------------+
|  Existing Safety Runtime (UNCHANGED)                                 |
|                                                                      |
|  ask / edit / apply / fix / run / status / task / profile / resume / |
|  commit / memory / debug / audit / checkpoint / rollback /           |
|  AgentOrchestrator / PatchValidator / CheckpointManager / Policy /   |
|  ShellRunner / AuditLogger / DirtyTreeGuard / ContextSelector        |
+--------------------------------+-------------------------------------+
                                 |
                                 v
+----------------------------------------------------------------------+
|  Provider layer (UPGRADED)                                           |
|  - factory.create_llm_client(): adds "deepseek" preset               |
|  - OpenAICompatibleLLMClient: gains rate-limit-aware retry,          |
|    configurable per-call timeout, structured progress callback       |
|  - Doctor: provider diagnostics (key, base URL, model, net policy)   |
|  - Optional live smoke: sac smoke live-provider                      |
+----------------------------------------------------------------------+
```

Three architectural rules:

1. The orchestration layer **calls** existing commands/services. It never
   bypasses `PatchValidator`, `CheckpointManager`, `AuditLogger`, the policy
   gate, or the dirty-tree guard.
2. Every mutating action stops at a `HumanCheckpoint` unless the user has
   pre-approved it for that specific step (no global auto-apply switch).
3. Every new surface is **EXPERIMENTAL** and ships behind feature flags or
   experimental CLI labels. No new stable contracts are promoted in v4.10-v4.12.

### v4.10.x - DeepSeek Provider + Reliability

Objective: make a real LLM usable end-to-end with credible reliability,
without weakening the existing network-policy or mock-default posture.

#### v4.10.0 - DeepSeek provider preset

- **Objective.** Add `provider = "deepseek"` to the factory **and** to
  `OpenAICompatibleLLMClient`. The factory wiring alone is not sufficient
  because the current client (`src/safecode/llm/openai_client.py:51`)
  reads only `OPENAI_API_KEY` / `SAFECODE_LLM_API_KEY` and POSTs directly
  to `config.llm.base_url` (`src/safecode/llm/openai_client.py:149`);
  DeepSeek needs `DEEPSEEK_API_KEY` and a `/v1/chat/completions` join.
- **Files / modules.**
  - `src/safecode/llm/deepseek.py` (new, ~80 LoC): preset table mapping
    `deepseek` -> `{base_url: "https://api.deepseek.com", default_model:
    "deepseek-v4-pro", fallback_model: "deepseek-v4-flash",
    api_key_env: "DEEPSEEK_API_KEY"}`. The `fallback_model` is recorded for
    future use (config-overridable, opt-in); v4.10.0 only consumes
    `default_model`. Model id is overridable by config. Legacy model names
    such as `deepseek-chat` and `deepseek-reasoner` are accepted by config
    but are **not** the recommended defaults for this roadmap.
  - `src/safecode/llm/factory.py` (edit): add `_DEEPSEEK_PROVIDERS =
    frozenset({"deepseek"})`; route to `OpenAICompatibleLLMClient` using
    preset defaults when config fields are blank; never overwrite explicit
    user config. The factory passes the resolved `api_key_env` and the
    raw `base_url` through to the client (see client edits below).
  - `src/safecode/llm/openai_client.py` (edit, required for this batch):
    - **`api_key_env` resolution.** Accept a provider-supplied
      `api_key_env` (default `"OPENAI_API_KEY"`); resolve in this order:
      `os.getenv(api_key_env)` -> `os.getenv("OPENAI_API_KEY")` ->
      `os.getenv("SAFECODE_LLM_API_KEY")`. This preserves existing
      behavior for the `openai` / `openai-compatible` providers while
      letting `deepseek` pick up `DEEPSEEK_API_KEY` first. The env var
      name is the only thing flowing through; the secret itself is never
      logged, echoed, or written to disk.
    - **Endpoint normalization.** The client builds the request URL by
      joining `/v1/chat/completions` onto `config.llm.base_url`. The
      DeepSeek preset stores `https://api.deepseek.com` without the
      `/v1` suffix; the client must produce
      `https://api.deepseek.com/v1/chat/completions`. The join must
      defensively detect and avoid double-appending when a caller has
      already supplied a path ending in `/v1`, `/v1/`, or
      `/v1/chat/completions`. Behavior for callers that already supply
      a full path (e.g., legacy `openai-compatible` configs that pasted
      `https://example.com/v1/chat/completions` into `base_url`) must
      not change. Network-policy assertion still runs against the raw
      `config.llm.base_url` first; the joined path is the wire request.
  - `src/safecode/config.py` (edit): document `deepseek` in the provider
    docstring; no schema change required (existing fields suffice).
- **Endpoint normalization summary.** The provider preset itself never
  embeds `/v1`. All `/v1/chat/completions` construction is the client's
  responsibility (see the `openai_client.py` task above), and is governed
  by the defensive-join rule. This invariant is asserted in tests.
- **DeepSeek V4 response compatibility (caution, not implementation).**
  DeepSeek V4 may return reasoning/thinking-related fields depending on API
  mode. The resume MVP keeps the first DeepSeek integration conservative:
  use the standard OpenAI-compatible ChatCompletions path, normalize
  unknown response fields safely (ignore or pass-through; never crash),
  and avoid requiring multi-turn reasoning-content replay unless the
  existing `OpenAICompatibleLLMClient` explicitly supports it. This caution
  is roadmap guidance for v4.10.0; no extra implementation is required
  beyond defensive parsing.
- **CLI surfaces.** None new. `sac config show` already prints provider; new
  preset must appear there.
- **Data model / state.** No new persisted state; preset is a pure function.
- **Safety invariants.**
  - Network policy gate remains the sole authority for whether the real call
    can go out. The preset only resolves defaults; it never enables network.
  - API key resolution is env-only; never logged or echoed.
  - Mock remains the default provider; preset selection requires explicit
    config or wizard input.
- **Tests.**
  - `tests/test_llm_deepseek_preset.py` (new, ~15 tests): factory returns
    `OpenAICompatibleLLMClient`; base URL/model defaults applied; explicit
    config wins over preset; missing env key surfaces an actionable error
    that names `DEEPSEEK_API_KEY` (not `OPENAI_API_KEY`) for the
    `deepseek` provider; `provider = "deepseek"` round-trips through
    `SafeCodeConfig`.
  - `tests/test_openai_client_endpoint.py` (new, ~10 tests): client joins
    `/v1/chat/completions` onto `https://api.deepseek.com`; does **not**
    double-append when `base_url` already ends in `/v1`, `/v1/`, or
    `/v1/chat/completions`; preserves legacy callers' full URLs;
    `api_key_env` resolution falls back to `OPENAI_API_KEY` then
    `SAFECODE_LLM_API_KEY`; secrets never appear in error text or repr.
- **Docs.** Add `## DeepSeek` section to `docs/providers.md` (env var, base
  URL, recommended model id, advisory note that DeepSeek is experimental as
  a provider preset).
- **Validation.** `PYTHONPATH=src python3 -m pytest -q tests/test_llm_deepseek_preset.py`,
  then full `PYTHONPATH=src python3 -m pytest -q`.
- **Commit / tag.** Branch `v4.10.0-deepseek-preset`, tag `v4.10.0`.

#### v4.10.2 - Provider doctor

- **Objective.** `sac doctor` reports a per-provider readiness section so the
  user can diagnose failed real-LLM calls without reading source.
- **Files.**
  - `src/safecode/doctor.py` (extend): `_provider_diagnostics()` returns one
    diagnostic each for: API key present (env var only, never echoed),
    base URL resolvable (format/parse check only, **no network call**),
    model id configured, network policy **statically permits the configured
    provider host** (policy-document inspection only, no DNS or connect),
    and last-session token/cost summary **if available — SKIP if metrics
    are disabled or cost accounting has not been implemented yet**.
  - `src/safecode/llm/deepseek.py`: add `describe()` helper used by doctor.
- **CLI surfaces.** `sac doctor` output gains a `Provider` section; `--json`
  output gains a `provider` key. No new top-level command.
- **Safety invariants.** Doctor's new `Provider` section must not make any
  provider network request. It inspects config, env, and network policy
  only. The opt-in real round-trip path is `sac smoke live-provider`
  (v4.10.4), which is the **only** command in this train that touches a
  provider endpoint and only with an explicit env gate.

  **Existing PyPI update check (`src/safecode/doctor.py:204`).** Doctor
  today performs a PyPI update check that does reach the network. v4.10.2
  does **not** silently remove it, but it must be made offline-safe and
  decoupled from provider diagnostics:

  - The PyPI update check is moved behind an opt-out env knob
    `SAFECODE_DOCTOR_UPDATE_CHECK` (default `1`; set to `0` to skip).
  - It already returns `SKIP` on any network failure; that behavior is
    preserved and asserted in tests.
  - It is rendered in a separate `Release` / `Updates` section, not under
    `Provider`. The `Provider` section is statically computed.
  - The user-facing doctor copy is updated to read: "doctor does not make
    provider network requests" (precise) rather than "doctor makes no
    network call" (false, given the update check).

  The static/provider split for this train is then:

  ```text
  sac doctor              -> static config/env/policy + optional PyPI
                             update check; never contacts a provider
  sac smoke live-provider -> opt-in real provider round-trip, requires
                             SAFECODE_LIVE_SMOKE=1 and a non-mock provider
  ```
- **Tests.** `tests/test_provider_doctor.py` (new, ~12 tests): each field PASS
  / SKIP / FAIL outcome; mock provider yields a PASS section indicating
  deterministic mode; secrets never printed; provider section is
  computed without any outbound HTTP (asserted by patching urlopen and
  expecting zero calls within the provider path). `SAFECODE_DOCTOR_UPDATE_CHECK=0`
  skips the PyPI update check entirely.
- **Docs.** README "Doctor" section gains a Provider line; troubleshooting
  documents each FAIL message.
- **Validation.** `pytest -q tests/test_provider_doctor.py` then full suite.
- **Commit / tag.** `v4.10.2`.

### v4.11.x - Agentic-Lite Task Loop

Objective: a controller that turns a natural-language goal into a plan, then
executes steps through existing SafeCode commands with explicit human approval
at every mutation and a validation loop on every code change.

The controller is **thin**. If a step is "propose a patch", it calls the same
code path `sac edit` uses. If a step is "run tests", it calls the same code
path `sac run --suite test` uses. There is no shadow code path.

#### v4.11.0 - Typed step model on existing AgentLoop

- **Objective.** Add the typed step / action / result model **as an
  evolution of the existing `AgentLoop`** at
  `src/safecode/agent/loop.py:58`, not as a parallel orchestrator. The
  current `AgentLoop` already implements `step()` / `run()` returning
  `AgentStepResult` / `AgentRunResult`, already records to
  `AgentJournalStore`, already pauses for patch approval, and already
  honors v4.4 `TaskBudgetStore`. This batch puts a typed `kind` /
  `status` layer on top so v4.11.3+ can branch on step kind and the
  validation loop has something to react to.
- **Files.**
  - `src/safecode/agent/step_model.py` (new, ~120 LoC):
    - `AgentStepKind = Literal["plan","ask","edit","apply","run","fix",`
      `"commit","rollback","mcp_call","subagent_dispatch","stop"]`.
    - `AgentStepStatus = Literal["success","blocked","approved",`
      `"rejected","failed","interrupted","waiting_for_user"]`.
    - `TypedAgentStep(BaseModel)`: `index`, `kind`, `description`,
      `requires_approval` (bool), `created_at`, `payload_version=1`.
      Derivation rules: `apply|commit|rollback|edit|run|fix` =>
      `requires_approval=True` unconditionally.
    - `TypedAgentStepResult(BaseModel)`: `step_index`, `kind`, `status`,
      `summary`, `audit_trace_id`, `pending_patch_id`,
      `failure_category` (reuses v4.7 taxonomy), `payload_version=1`.
    These are the **typed projection** of the existing
    `AgentStepResult` dataclass; the legacy dataclass remains for
    backward compatibility and is wrapped, not removed.
  - `src/safecode/agent/loop.py` (edit, narrow): extend `AgentLoop` so
    that every existing step path (read-only routing, MCP read,
    subagent dispatch, patch proposal, MCP approved write) computes a
    `TypedAgentStep` + `TypedAgentStepResult` alongside the existing
    `AgentStepResult`. The legacy return type is unchanged; the typed
    projection is exposed via a new `last_typed_result` property and
    fed into the journal (see v4.11.1) and the validation loop (see
    v4.11.3). No existing test should need to change.
  - `src/safecode/agent/__init__.py` (edit): export `TypedAgentStep`,
    `TypedAgentStepResult`, `AgentStepKind`, `AgentStepStatus`.
- **CLI surfaces.** None yet — this batch keeps `sac agent step` /
  `sac agent run` behavior identical. v4.11.2 surfaces typed kinds in
  `--json` output.
- **Data model.** `TypedAgentStep` / `TypedAgentStepResult` are Pydantic
  models with `payload_version = 1`. Persisted only via the journal
  extensions in v4.11.1; not added to `AgentSessionState` yet.
- **Safety invariants.**
  - `AgentLoop` continues to call existing services. The typed layer is
    a **classifier** over existing routing; it never reads or writes
    files outside what those services already do.
  - The kind set `{edit, apply, run, fix, commit, rollback}` has
    `requires_approval = True`, asserted in unit tests.
  - **Hard rule for mutating execution.** A `TypedAgentStep(kind="apply"
    | "commit" | "rollback")` may be **generated** as a suggested next
    step, but `AgentLoop` must not **execute** it unless there is an
    explicit interactive approval bound to all of:
    1. the exact `task_id` (from `TaskStore.current_id()`),
    2. the specific `step_index`,
    3. the current pending patch hash (for `apply` — reuses
       `PatchPendingAction` patch_id binding) **or** the current task
       file set (for `commit`) **or** the selected checkpoint id (for
       `rollback`),
    4. the current working tree state (dirty-tree guard hash).
    Any mismatch on any of these four bindings invalidates the approval
    and the loop must re-prompt or stop. There is **no** global
    auto-apply or auto-commit switch. The `apply` binding already
    exists via `PatchPendingAction`; the `commit` and `rollback`
    bindings are added in this batch to bring them up to the same bar.
  - On `RecoverableContractFailure` after retry (the existing bounded
    retry path), the loop stops with `failure_category =
    "model_output_invalid"` and never retries silently a second time
    (existing behavior, now also recorded in the typed result).
  - The loop attaches every action to the current `TaskState` and
    writes a `task_id` on every audit event (existing v4.1.1 wiring).
- **Tests.** `tests/test_agent_loop_typed_steps.py` (~25 tests): existing
  `AgentLoop.step()` behaviors classify into the expected `kind`;
  approval-required kinds are flagged; rejected approval records
  `status="rejected"` and does not call the underlying service; the
  loop stops on `model_output_invalid` after one retry. Safety tests
  required:

  - `AgentLoop` cannot execute `apply` without an approval token bound
    to the current pending patch hash; a stale or mismatched hash forces
    re-approval. (Already enforced via `PatchPendingAction` —
    test promotes the invariant.)
  - `AgentLoop` cannot execute `commit` without explicit approval bound
    to the current task file set; adding or removing files between
    approval and execution invalidates the token.

## 6. Future Evolution Toward Claude Code Parity

The v4.10-v4.12 architecture is intentionally additive. Each Claude Code-like
capability maps to a future train without contradicting MVP choices:

| Claude Code capability         | How v4.12 architecture extends                                                                                 |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Hooks (`after_apply`, etc.)    | v4.13: new hook events fire from `AgentLoop` typed-step boundaries; existing `hooks/` policy applies unchanged.|
| Skills (`python`, `test-fix`)  | v4.14: skills register `TypedAgentStep` factories the loop can consult during planning; pure additive.         |
| Sub-agents                     | Reuse v3.4 `SubagentPool`; `AgentLoop` already dispatches sub-agents — future work extends to parallel fan-out.|
| Multi-language symbol index    | v4.15: extra indexers feed the existing `ContextSelector`; no change to the loop.                              |
| Better context ranking (BM25)  | v4.16: pure-Python BM25 layered into `ContextSelector`; embedding-free; preserves bounded context budget.      |
| Real MCP tool execution        | v4.18: `TypedAgentStep(kind="mcp_call")` already routes through existing MCP write-proposal flow.              |
| IDE integration                | Existing v3.5 LocalAPI JSON-RPC bridge already exposes the safety primitives; v4.17 adds an `agent_run` method.|
| Cloud / background tasks       | Agent journal is portable; a remote runner becomes a different *executor* of the same `TypedAgentStep` model.  |
| Push / PR automation           | Sits above `sac commit`; gated behind a separate trust review and remains opt-in.                              |
| Live observability             | Reuse v3.6 OTel exporter and v3.10 metrics writer; emit `TypedAgentStep` events through the same channels.     |

Critically, the typed step model on `AgentLoop` is the **only** new
abstraction. Every advanced capability above is a new producer or
consumer of `TypedAgentStep` events on the existing loop, not a parallel
orchestration system.

## 7. Cross-Cutting Conventions

- Branch names: `vX.Y.Z-short-feature-name` (no `codex/` prefix; existing
  rule).
- Each batch ends with a tag, a version-note file, and a matrix-row update.
- Default LLM provider in tests stays `mock`; live tests stay opt-in via
  `SAFECODE_LIVE_TESTS=1` / `SAFECODE_LIVE_SMOKE=1`.
- No new stable contract is promoted in v4.10-v4.12. The next contract-cut
  audit is deferred to a separate post-MVP plan.
- Safety invariants on every batch: patch parsing → diff → checkpoint →
  approval → apply → audit → rollback path is preserved; dirty-tree guard is
  preserved; policy gate is preserved; network policy is preserved.

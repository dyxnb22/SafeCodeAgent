# v5.4 → v5.5 Product Roadmap: MCP Depth and Production

## Context

After v5.3.2, SafeCode Agent achieves terminal experience parity with Claude
Code and Codex CLI: trust modes, context intelligence, display quality, and
a complete safety infrastructure. The v5.4–v5.5 trains address the two
remaining structural gaps for a terminal-only tool:

| Gap | Symptom | Train |
|---|---|---|
| MCP is shallow | Read-only, single server, no real agentic tool extension | v5.4.x |
| Not production-distributed | No PyPI release, no Homebrew, no signing CI | v5.5.x |

**Scope decision:** IDE integration (VS Code extension) is explicitly out of
scope. SafeCode Agent is a **terminal tool**. The JSON-RPC bridge
(`sac api jsonrpc`) and the VS Code extension skeleton remain in the repo as
experimental artifacts but will not be actively developed or published.

## v5.4.x: MCP Depth

### Theme

The Model Context Protocol (MCP) is the ecosystem standard for extending
agents with external tools and data sources. SafeCode has experimental MCP
read support since v3.3.x, but the current state is far behind Claude Code:

- Only stdio transport; no HTTP/SSE transport.
- Read-only; write tools are approval-gated but the flow is incomplete.
- `MCPLifecycleManager` starts/stops servers but isn't wired into the
  agent loop.
- The agent can't actually call MCP tools in a multi-tool turn — the
  `NativeToolDispatcher` and MCP are completely separate paths.

**Goal:** A user can add a third-party MCP server (e.g., `sqlite`,
`brave-search`, `filesystem`) and the agent will call it as naturally as it
calls `read_file`, with the same audit/redaction/policy guards.

### v5.4.0 — mcp-native-tool-bridge

**What:** Bridge the MCP read-only runner into `NativeToolDispatcher`
so MCP tools appear as native tools in the agent's tool list.

**Implementation:**

- New `src/safecode/mcp/native_bridge.py`:
  - `MCPNativeToolBridge(runner: MCPReadOnlyRunner, server: str)`: wraps one
    MCP server's tools as `NativeToolSpec` instances.
  - `discover_and_register(dispatcher: NativeToolDispatcher)`: calls
    `MCPReadOnlyRunner.discover_tools()`, converts each to a `NativeToolSpec`
    (with `experimental=True`, `audit_event_type="tool_call_mcp_read"`),
    and registers it with the dispatcher.
  - Tool name collision policy: prefixed as `mcp_<server>_<tool>` to avoid
    conflicts with built-in tools.

- `register_mcp_tools(dispatcher, project_root)` wired into `AgentOrchestrator`
  alongside `register_read_tools`, `register_write_tools`, etc.

- `sac mcp list-native`: lists all MCP tools currently registered with the
  dispatcher (new read-only CLI command).

**Safety invariants:**
- MCP tool outputs still pass through `redact_secrets()` before model context.
- Classification gate (`classify_mcp_tool`) still runs before every call.
- Write-class MCP tools remain blocked by the read-only runner.
- `MCPServerConfig.scope = "denied"` servers are never registered.

**Tests:** `tests/test_mcp_native_bridge.py` (~12 cases)

### v5.4.1 — mcp-write-execution

**What:** Promote MCP write execution from "proposal-stored-in-approval-dir"
to a first-class approval flow parallel to `edit_file`.

**Current state:** `MCPApprovalStore` (v3.8.2) stores single-use grants; the
execute-granted-write path exists but is not surfaced in `sac shell` or the
agent loop.

**Target state:** In `sac shell`, when the agent calls an MCP write tool:
1. A `StopForUserAction` is emitted with the tool name, server, and input.
2. User types `y` to approve; a single-use grant is stored.
3. `MCPReadOnlyRunner.execute_granted_write()` consumes the grant and executes.
4. Result returned to the model as a `NativeToolResult`.
5. Audited as `mcp_granted_write_*` events (already implemented in v3.8.2).

**New `sac mcp execute` CLI:** one-shot execute for scripting:
`sac mcp execute <server> <tool> --input '{"key":"val"}' --grant-id <id>`.
Never executes without a valid grant ID.

**Scope gates unchanged:** `scope = "read_only"` blocks write proposals;
`scope = "write_proposal_required"` allows them through this new flow.

**Tests:** `tests/test_mcp_write_execution.py` (~10 cases)

### v5.4.2 — mcp-docs

**What:** Docs cut for the MCP depth train.

- README: "MCP Integration (v5.4, EXPERIMENTAL)" section — adding servers,
  native tool bridge, write approval flow.
- MVP guide: "Extending the agent with MCP servers" walkthrough using the
  `sqlite` MCP server as the example.
- Troubleshooting:
  - "MCP tool not showing in /tools" — server not started, scope=denied,
    or discovery failed.
  - "MCP write tool blocked" — scope must be `write_proposal_required`.
  - "MCP tool name collision" — `mcp_<server>_<tool>` prefix policy.
- `docs/providers.md`: MCP server configuration reference.
- Matrix: three new rows.

## v5.5.x: Production Readiness

### Theme

Everything in v5.0–v5.4 is developed from a source checkout. v5.5.x makes
SafeCode Agent installable as a proper release artifact: a signed PyPI wheel
and a Homebrew formula, with a CI pipeline that publishes on tag.

This train has no new agent features. It is the last thing before a public
"v1.0" announcement.

### v5.5.0 — pypi-release

**What:** First production PyPI publish with artifact signing.

- Resolve any remaining dependency version pins for a clean sdist/wheel.
- `sac release publish` already exists (v3.6.1); wire it into a GitHub Actions
  `release` job triggered on `v*.*.0` tag push.
- Signing: detached `cosign` or `gpg` signature for the wheel, matching the
  mechanism documented in `docs/install-update.md` (v3.9.0 decision).
- `SAFECODE_PUBLISH=1` guard remains; the CI job sets it as a repo secret.
- Update README install section: `pipx install safecode-agent`.

**Acceptance:** `pipx install safecode-agent` from PyPI gives a working `sac`
with `sac doctor` exiting 0.

**Tests:** CI `release` job green on a dry-run tag; `tests/test_ci_matrix.py`
extended to verify the release job config.

---

### v5.5.1 — homebrew-formula

**What:** A Homebrew formula for macOS.

- Create `Formula/safecode-agent.rb` in a `homebrew-safecode` tap repo.
- Formula installs from the PyPI wheel via `pipx` shim (simplest approach;
  avoids embedding Python version assumptions in the formula).
- `scripts/update-brew-formula.sh` auto-generates the formula from the
  current version and SHA256 of the published wheel.
- README: `brew install safecode/tap/safecode-agent`.
- `sac release publish` gains `--update-brew` flag to regenerate the formula.

**Acceptance:** `brew install safecode/tap/safecode-agent && sac doctor` exits 0.

---

### v5.5.2 — production-docs

**What:** Final docs cut and project status update.

- `docs/install-update.md`: full install matrix:
  - `pipx install safecode-agent` (PyPI — recommended)
  - `brew install safecode/tap/safecode-agent` (macOS)
  - `uv build && pipx install dist/<wheel>` (offline)
  - `git clone + uv sync` (source dev)
- `docs/project-final-status-and-roadmap.md`: updated to reflect v5.5.x as
  the production baseline. Explicitly states:
  - All B-series reliability bugs closed.
  - Terminal experience parity with Claude Code / Codex CLI.
  - 16 stable contracts documented and tested.
  - MCP integration at parity with basic server use.
  - Distributed via PyPI and Homebrew.
  - SafeCode is a **terminal-only tool** by design — no IDE extension planned.
  - **Explicitly deferred post-v5.5:**
    computer use, RAG/embeddings, multi-repo context, remote background agents,
    JetBrains/VS Code plugins, Anthropic MCP server exposure.
- README: "Status" badge updated to "Production (v5.5)".
- Matrix: three new rows.

## Explicitly Deferred After v5.5.2

| Item | Reason |
|---|---|
| **VS Code / JetBrains plugin** | SafeCode is a terminal tool by design |
| **Computer use / screenshot input** | Requires multimodal model + screen permission model |
| **RAG / embeddings / vector search** | High complexity; import graph + git context covers the common case |
| **Multi-repo context** | Requires cross-repo path validation redesign |
| **Remote / background agents** | Requires server infrastructure |
| **Anthropic MCP server (expose SafeCode as MCP)** | Reverses client direction; separate product |
| **Evals on real codebases** | Requires real provider credentials + reproducible test repos |

| Gap | Claude Code | SafeCode after v5.5 |
|---|---|---|
| Trust modes | ✅ | ✅ (v5.1) |

| Context intelligence | ✅ | ✅ (v5.3: git + import graph + compaction) |
| MCP integration | ✅ full | ✅ good enough (v5.4) |
| Audit + rollback | ❌ none | ✅ **differentiator** |

| PyPI / Homebrew | ✅ | ✅ (v5.5) |

SafeCode's enduring advantage: **audit trail + checkpoint rollback + policy-gated
commands** — the properties that matter most for team and enterprise use — with
no IDE dependency required.

# v5.4 → v5.6 Product Roadmap: MCP Depth, IDE, and Production

## Context

After v5.3.2, SafeCode Agent achieves terminal experience parity with Claude
Code and Codex CLI: trust modes, context intelligence, display quality, and
a complete safety infrastructure. The v5.4–v5.6 trains address the remaining
structural gaps:

| Gap | Symptom | Train |
|---|---|---|
| MCP is shallow | Read-only, single server, no real agentic tool extension | v5.4.x |
| No IDE integration | VS Code extension skeleton exists but doesn't ship | v5.5.x |
| Not production-distributed | No PyPI release, no Homebrew, no signing CI | v5.6.x |

These trains are lower-urgency than v5.1–v5.3 (which close the daily-use
experience gap) but are required for SafeCode to be a product people can
actually install and use beyond "clone the repo".

---

## v5.4.x: MCP Depth

### Theme

The Model Context Protocol (MCP) is the ecosystem standard for extending
agents with external tools and data sources. SafeCode has experimental MCP
read support since v3.3.x, but the current state is far behind Claude Code:

- Only stdio transport; no HTTP/SSE transport.
- Read-only; write tools are approval-gated but the flow is incomplete.
- `MCPLifecycleManager` starts/stops servers but isn't wired into the
  agent loop.
- The agent can't actually call MCP tools in a multi-tool turn — the
  `NativeToolDispatcher` and MCP are completely separate paths.

**Goal:** A user can add a third-party MCP server (e.g., `sqlite`, `brave-search`,
`filesystem`) and the agent will call it as naturally as it calls `read_file`.

### v5.4.0 — mcp-native-tool-bridge

**What:** Bridge the MCP read-only runner into the `NativeToolDispatcher`
so MCP tools appear as native tools in the agent's tool list.

**Implementation:**

- New `src/safecode/mcp/native_bridge.py`:
  - `MCPNativeToolBridge(runner: MCPReadOnlyRunner, server: str)`: wraps one
    MCP server's tools as `NativeToolSpec` instances.
  - `discover_and_register(dispatcher: NativeToolDispatcher)`: calls
    `MCPReadOnlyRunner.discover_tools()`, converts each discovered tool to a
    `NativeToolSpec` (with `experimental=True`, `audit_event_type="tool_call_mcp_read"`),
    and registers it with the dispatcher.
  - Tool name collision policy: prefixed as `mcp_<server>_<tool>` to avoid
    conflicts with built-in tools.

- `register_mcp_tools(dispatcher, project_root)` wired into `AgentOrchestrator`
  alongside `register_read_tools`, `register_write_tools`, etc.

- `sac mcp list-native`: lists all MCP tools currently registered with the
  dispatcher (new read-only CLI command).

**Safety invariants:**
- MCP tool outputs still run through `redact_secrets()` before model context.
- Classification gate (`classify_mcp_tool`) still runs before every call.
- Write-class MCP tools remain blocked by the read-only runner.
- `MCPServerConfig.scope = "denied"` servers are never registered.

**Tests:** `tests/test_mcp_native_bridge.py` (~12 cases)

---

### v5.4.1 — mcp-write-execution

**What:** Promote MCP write execution from "proposal-stored-in-approval-dir"
to a first-class approval flow parallel to `edit_file`.

**Current state:** `MCPApprovalStore` (v3.8.2) stores single-use grants; the
execute-granted-write path exists but is not surfaced in `sac shell` or
the agent loop.

**Target state:** In `sac shell`, when the agent calls an MCP write tool:
1. A `StopForUserAction` is emitted with the tool name, server, and input.
2. User types `y` to approve; a single-use grant is stored.
3. `MCPReadOnlyRunner.execute_granted_write()` consumes the grant and executes.
4. Result returned to the model as a `NativeToolResult`.
5. Audited as `mcp_granted_write_*` events (already implemented).

**New `sac mcp execute` CLI:** surface the one-shot execute path as a hidden
command for scripting: `sac mcp execute <server> <tool> --input '{"key":"val"}'
--grant-id <id>`. Never executes without a valid grant ID.

**Scope gates unchanged:** `scope = "read_only"` blocks write proposals;
`scope = "write_proposal_required"` allows them through this new flow.

**Tests:** `tests/test_mcp_write_execution.py` (~10 cases)

## v5.5.x: VS Code Extension

### Theme

SafeCode has a VS Code extension skeleton since v3.9.2 (`vscode-extension/`),
but the VSIX has never been built or published. The extension uses the existing
`sac api jsonrpc` stdio bridge; no new server protocol is needed.

The goal for v5.5.x is a **shippable VSIX** that a developer can install from
a `.vsix` file (not necessarily the marketplace) and use for the core
ask/edit/apply/rollback workflow from within VS Code.

### v5.5.0 — vsix-build-and-local-install

**What:** A buildable, locally-installable VSIX.

- Fix any TypeScript compilation errors in `vscode-extension/src/extension.ts`.
- Add `npm run package` script using `vsce package`.
- Add `scripts/build-vsix.sh` that runs `npm ci && npm run package` and
  outputs to `dist/safecode-agent-*.vsix`.
- CI: add `vsix-build` job (advisory `continue-on-error: true` until stable).
- `tests/test_ide_extension_manifest_contract.py`: extend to verify the
  built manifest (if the VSIX file exists at CI time).
- **Not included:** marketplace publish, auto-update, auth flows.

**Acceptance:** `scripts/build-vsix.sh` succeeds on a clean checkout.
Local install: `code --install-extension dist/safecode-agent-*.vsix`.

**Tests:** `tests/test_vsix_build.py` (~5 cases, mostly manifest guards)

---

### v5.5.1 — extension-core-commands

**What:** The five core commands working end-to-end through the JSON-RPC bridge.

| VS Code Command | Maps to |
|---|---|
| `safecode.ask` | `sac ask` via `jsonrpc.ask()` |
| `safecode.edit` | `sac edit` via `jsonrpc.edit()` |
| `safecode.apply` | `sac apply` via `jsonrpc.apply()` |
| `safecode.rollback` | `sac rollback --last` via `jsonrpc.rollback()` |
| `safecode.status` | `sac status` via `jsonrpc.report()` |

**Approval flow in VS Code:** when `edit()` returns a pending patch, the
extension opens VS Code's native diff editor (`vscode.diff()`) to show the
proposed change. The user clicks "Apply" or "Reject" in the diff editor.

**Security:** the extension never stores API keys; it spawns `sac` as a
subprocess with the user's environment. Credentials stay in env vars or the
system keychain (via `sac provider add --store keychain`).

**Tests:** `tests/test_ide_bridge_jsonrpc.py` extended (~5 new cases)

## v5.6.x: Production Readiness

### Theme

Everything in v5.0–v5.5 is developed from a source checkout. v5.6.x makes
SafeCode Agent installable as a proper release artifact: a signed PyPI wheel,
a Homebrew formula, and a CI pipeline that publishes on tag.

This train is purely infrastructure — no new agent features. It is the last
thing before a public "v1.0" announcement.

### v5.6.0 — pypi-and-signing

**What:** First production PyPI publish + artifact signing.

- Resolve any remaining dependency version pins for a clean sdist/wheel.
- `sac release publish` already exists (v3.6.1); wire it into a GitHub Actions
  `release` job triggered on `v*.*.0` tag push (major releases only, not patches).
- Signing: `cosign` or `gpg` detached signature for the wheel, matching the
  mechanism documented in `docs/install-update.md` (v3.9.0 decision: not Sigstore Rekor).
- `SAFECODE_PUBLISH=1` guard remains required; the CI job sets it as a secret.
- Update README install section to reference PyPI: `pipx install safecode-agent`.

**Acceptance:** `pip install safecode-agent` from PyPI gives a working `sac`.

---

### v5.6.1 — homebrew-formula

**What:** A Homebrew formula for macOS.

- Create `Formula/safecode-agent.rb` in a tap repository
  (`homebrew-safecode` or similar).
- Formula installs from the PyPI wheel (simplest: `pipx` shim) or from
  source via `pip install`.
- `scripts/update-brew-formula.sh` auto-generates the formula from the
  current version and SHA256 of the published wheel.
- Add to README: `brew install safecode/tap/safecode-agent`.
- `sac release publish` gains `--update-brew` flag.

**Acceptance:** `brew install safecode/tap/safecode-agent && sac doctor` exits 0.

## Explicitly Deferred After v5.6.2

The following are NOT in this roadmap. They require either external partnerships,
significant infrastructure investment, or a new product direction decision:

| Item | Reason for Deferral |
|---|---|
| **Computer use / screenshot input** | Requires multimodal model support + screen access permission model |
| **JetBrains plugin** | Separate Kotlin/Java implementation; no shared VS Code infra |
| **RAG / embeddings / vector search** | Requires vector DB dependency; high complexity for uncertain ROI at target scale |
| **Multi-repo context** | Requires cross-repo path validation redesign |
| **Remote/background agents** | Requires server infrastructure + cloud credentials |
| **Anthropic MCP server (exposing SafeCode as MCP)** | Requires server mode; reverses the client direction |
| **Prompt engineering / system prompt tuning** | Depends on which model is active; model-specific, not platform work |
| **Evals on real codebases** | Requires real provider credentials + reproducible test repos |

After v5.6.2, the remaining gaps vs Claude Code will be:

| Gap | Claude Code | SafeCode after v5.6 |
|---|---|---|
| Computer use | ✅ screenshot/UI | ❌ deferred |
| JetBrains IDE | ✅ | ❌ deferred |
| Semantic search | ✅ (via embeddings) | ⚠️ import graph + git only |
| Remote agents | ✅ (Projects) | ❌ deferred |
| Model quality | ✅ (Anthropic-tuned) | ⚠️ depends on provider |
| Trust modes | ✅ | ✅ (v5.1) |
| Audit + rollback | ❌ (no checkpoint) | ✅ differentiator |
| Policy gates | ❌ (no risk classification) | ✅ differentiator |
| MCP depth | ✅ full | ✅ (v5.4, good enough for daily use) |
| IDE (VS Code) | ✅ (marketplace) | ⚠️ (v5.5, local install only) |
| Cost tracking | ✅ | ✅ (v5.2) |

SafeCode's enduring advantage remains: **audit trail + checkpoint rollback +
policy-gated commands** — the properties that matter for team and enterprise use.

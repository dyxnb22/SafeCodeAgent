# v5.1 → v5.3 Product Roadmap: Terminal Experience Parity

## Context

v5.0.0 delivers **functional parity** with Claude Code and Codex CLI:
native tool calling, multi-tool turns, read/write/command tools, GitHub
integration, and a reliable checkpoint/audit/rollback infrastructure.

v5.1–v5.3 delivers **experience parity**: the approval model, display
quality, and context intelligence that make the agent *feel* like Claude
Code rather than merely *having the same capabilities*.

The gaps that separate a feature-complete v5.0 from a genuinely
comparable terminal experience:

| Gap | Symptom | Train |
|---|---|---|
| Agent loop not wired to multi-tool | `MultiToolTurnRunner` exists but `AgentLoop` doesn't use it | v5.1.x (prerequisite) |
| Approval friction | Every `edit_file` pauses for "y/n" — you feel the agent, not the flow | v5.1.x Trust Modes |
| Prompt caching missing | 3-5x higher token cost vs Claude Code in long sessions | v5.1.x (prerequisite) |
| Display quality | No file tree, no session cost, no compact diff view | v5.2.x Display Polish |
| Context intelligence | Agent doesn't know what to read; repeats itself; forgets earlier context | v5.3.x Context Intelligence |
| No git context | Agent can't read blame/log/diff; misses recent change context | v5.3.x |

---

## Pre-train Prerequisites (integrated into v5.1.0)

Two architectural gaps must be closed before trust modes are meaningful:

### P1: Wire AgentLoop to MultiToolTurnRunner

`MultiToolTurnRunner` (v4.22.0) exists as an independent class but
`AgentLoop.run()` and `AgentLoop.step()` still use the old one-step-per-call
pattern. Trust modes only make sense when the loop can dispatch multiple tool
calls per user message without stopping for approval on each one.

**Change:** Replace `AgentLoop.step()` with a multi-tool-turn dispatcher:
- In each loop iteration, call `MultiToolTurnRunner.run_turn()` rather than
  `choose_tool()` + single dispatch.
- `run_turn()` returns when the model emits `stop_for_user`/`answer`, or the
  20-tool cap is hit.
- Tool results feed back into the model's context automatically between calls.
- Existing `on_step` callback preserved for streaming UX.
- `AgentLoop.run()` now: collect context → run_turn → collect result → repeat.

**Risk:** Existing tests that step the loop one tool at a time may need
updating. Run targeted `tests/test_agent_loop*.py` and `tests/test_eval*.py`
before committing.

### P2: Prompt Caching (Anthropic `cache_control`)

The `AnthropicLLMClient` has tracked cache hit metadata since v3.2.3 but has
never sent `cache_control` headers. In long sessions (the typical auto-edit
scenario), this causes 3-5x higher token costs vs Claude Code.

**Change in `anthropic_client.py`:**
- `_messages()` and `_messages_with_tools()`: add `cache_control: {"type": "ephemeral"}`
  to the system prompt block and to the first `user` turn (the two most
  cache-effective positions for a coding session).
- `_record_usage()`: surface `cache_read_input_tokens` and
  `cache_creation_input_tokens` from Anthropic usage metadata.
- `sac version --json` `stable_contracts`: not promoted (caching is EXPERIMENTAL).

**Cost impact:** Anthropic caches system prompts after the first call; in a
10-turn session the effective per-call cost drops to ~20% of uncached.

## v5.1.x: Trust Modes

### Theme

Claude Code and Codex CLI operate in a **trust-then-audit** model: the
agent makes changes, you review at the end and can always undo. SafeCode
has historically been **approve-then-apply**. Both are safe. But the user
experience is completely different.

v5.1.x introduces optional trust modes that switch to the
trust-then-audit model while preserving the safety infrastructure. The
audit log, checkpoints, and rollback all still run — you just don't stop
at every edit.

SafeCode's advantage in trust mode over Claude Code: **you can always
`sac rollback --last` or `/undo` without any git magic**, even after a
multi-file session.

### v5.1.0 — agentic-loop-foundation

**What:** Close the two architectural prerequisites (P1 + P2 above) and
deliver `--auto-edit` mode. This version has the highest implementation
risk of the train because it touches the core agent loop.

**P1 — AgentLoop multi-tool wiring:** (see P1 above)

**P2 — Anthropic prompt caching:** (see P2 above)

**Auto-edit mode:** A new `--auto-edit` flag (and `/auto-edit` toggle in shell)
that auto-approves `edit_file` and `write_file` tool calls while still
prompting for `run_command` and all GitHub write operations.

**CLI surface:**

```
sac shell --auto-edit
sac ask "refactor the auth module" --auto-edit
```

Inside `sac shell`, toggle with `/auto-edit on` and `/auto-edit off`.
The current mode is shown in the shell prompt: `sac[auto-edit]> `.

**Behaviour:**

- `edit_file` and `write_file`: execute immediately without a
  `StopForUserAction`. A Rich progress line prints:
  `  ✓ edit_file  src/auth/login.py  (+12 / -4 lines)`
  This is non-interactive; the user sees what happened but is not blocked.
- `run_command`: still prompts (same as non-auto-edit mode).
- GitHub write tools (`github_create_pr`, `github_push_branch`): still
  prompt.
- High-risk shell commands: still blocked by policy regardless of mode.
- Checkpoints still created before every write. The diff preview is
  recorded to the audit log even though it is not displayed interactively.

**Safeguards specific to `--auto-edit`:**

1. Session checkpoint summary: when the shell exits or the command
   completes, print a one-line summary:
   `Session: 3 files edited · 2 commands run · checkpoints: cp-001, cp-002, cp-003`
   followed by: `Undo all edits: sac rollback --session <session_id>`
2. File count guard: if a single turn would auto-apply more than 10
   `edit_file` / `write_file` calls, pause and prompt:
   `"About to edit 14 files. Continue? [y/N]"`. This prevents runaway
   refactors from landing silently.
3. `--auto-edit` is not saved to config by default — it is session-scoped.
   To persist, pass `--auto-edit --save`. Persisted value lives in the user
   config, not the project config (project config cannot enable auto-edit
   without user-level permission).

**`sac rollback --session <id>`:**
New rollback target: roll back all checkpoints created in a named session
in reverse creation order. `session_id` is printed at session start and
end, and stored in each `CheckpointMetadata.session_id` field (additive,
backward compatible).

**Tests:** `tests/test_auto_edit_mode.py` (~15 cases)
- Auto-edit applies `edit_file` without prompt.
- `run_command` still prompts in auto-edit mode.
- File count guard fires at 10+ files.
- Session rollback undoes all checkpoints in order.
- `--save` persists auto-edit to user config.
- Project config cannot enable auto-edit.

### v5.1.1 — full-auto-mode

**What:** `--full-auto` mode auto-approves `edit_file`, `write_file`,
**and** `run_command` (within the existing shell policy). This is the
Codex CLI `--approval-mode full-auto` equivalent.

**CLI surface:**

```
sac shell --full-auto
sac ask "add pytest coverage to all untested modules" --full-auto
```

Inside `sac shell`: `/full-auto on` / `/full-auto off`.
Prompt shows: `sac[full-auto]> `.

**What still requires approval in `--full-auto`:**
- Commands classified as `high_risk` by the policy engine (unchanged).
- `github_create_pr` and `github_push_branch` (network + external side
  effects always prompt).
- `run_command` with `cwd` outside the project root (policy blocks).

**Additional safeguards over `--auto-edit`:**

1. **Command preview before execution:** even in full-auto mode, each
   `run_command` call prints a one-liner before executing:
   `  → run_command  pytest -q tests/`
   and the exit code after:
   `  ✓ exit 0 (0.8s)`
   The user can press Ctrl-C between the preview line and execution
   (there is a configurable 0.5s delay via `--command-delay-ms`).
2. **Full-auto requires explicit opt-in per session.** It cannot be the
   default. No `--save` flag for `--full-auto` (unlike `--auto-edit`).
   The user must pass it explicitly every session.
3. File count guard applies at 10 files (same as auto-edit).

**`--command-delay-ms` flag:** configurable 0–2000 ms grace period before
`run_command` executes in full-auto mode. Default 500 ms. Allows Ctrl-C
even in full-auto. Zero is allowed for CI/scripting use.

**Tests:** `tests/test_full_auto_mode.py` (~12 cases)
- High-risk command still blocked.
- GitHub write still prompts.
- Command delay fires; Ctrl-C during delay aborts the command cleanly.
- `--full-auto` cannot be persisted via `--save`.

## v5.2.x: Display Polish

### Theme

Even with trust modes, the visual experience of Claude Code is ahead:
it shows a compact file tree of edited files, inline diffs, and running
token costs. These are not safety features — they are the details that
make a tool *enjoyable* to use over many hours.

v5.2.x covers display and feedback quality. No new tools, no new trust
levels, no new safety changes.

### Known usability issues addressed in this train (from v4.18.2 audit)

| ID | Issue |
|---|---|
| U1 | No per-session token or cost counter; users can't see how much they're spending |
| U2 | No compact summary of which files were changed at the end of a session |
| U3 | Diff display during approval is verbose (full unified diff); hard to skim for large edits |
| U4 | No "file tree" view of edits like Claude Code shows |
| U5 | Shell prompt gives no hint about current task status |
| U6 | No `/cost` command in shell |
| U7 | Long `run_command` output floods the shell with no truncation or collapsing |

### v5.2.0 — session-cost-and-summary

**What:** Per-session token tracking and cost display.

**Token tracking:**
- Each LLM API call already has `cost.py` infrastructure (`LLMCostRecord`).
  Wire this to a `SessionCostAccumulator` in `AgentLoop` that sums input
  tokens, output tokens, and estimated cost across all calls in a session.
- Stored in `AgentSessionState.cost` (additive, backward compatible).

**Display:**
- Shell prompt: `sac[N · ~$0.03]> ` — turn count and running cost estimate.
  Update after every LLM call. Cost only shown when a real provider is
  active (hidden for mock).
- `/cost` in `sac shell`: print full breakdown:
  ```
  Session cost estimate
  ─────────────────────
  Input tokens:   12 340    ~$0.037
  Output tokens:    1 890   ~$0.028
  Total:                    ~$0.065
  Provider: anthropic · claude-sonnet-4-6
  ```
- `sac ask`/`sac edit` with `--json`: add `cost: {input_tokens, output_tokens, estimated_usd}` to the JSON envelope.
- At session end (shell `/exit` or command completion): print a one-line
  cost summary: `Cost: ~$0.04 (14k in / 2k out)`.

**Address U1, U6.**

**Tests:** `tests/test_session_cost.py` (~8 cases)

### v5.2.1 — edit-display-polish

**What:** Better display of file edits and command output.

**Compact diff view (U3):**
- When `edit_file` prompts for approval (in non-auto-edit mode), show a
  compact diff rather than the full unified diff: only the changed lines
  ± 3 context lines, with a `[+12 / -4]` header and "Show full diff? (d)"
  hotkey.
- In auto-edit mode (no approval), the Rich progress line
  `✓ edit_file  src/auth/login.py  (+12 / -4 lines)` is already compact.

**Session edit summary (U2, U4):**
- At the end of each turn or on `/history`, print a file-tree-style
  summary of edits made so far:
  ```
  Files changed this session
  ├── src/auth/
  │   ├── login.py       edited (+12/-4)
  │   └── session.py     created
  └── tests/
      └── test_auth.py   edited (+31/-0)
  ```
  Uses Rich `Tree` widget. Paths are relative to project root.

**Command output collapsing (U7):**
- `run_command` output longer than 40 lines is collapsed by default:
  first 5 lines, `--- [N lines hidden] ---`, last 5 lines.
  Full output is written to the audit log. Hotkey `(o)` in interactive
  mode to expand.
- JSON output (`--json`) always includes full output (not collapsed).

**Shell prompt with task status (U5):**
- Shell prompt shows task status when a task is active:
  `sac[task:open · 2 iters]> ` — abbreviated task status and iteration
  count.

**Address U2, U3, U4, U5, U7.**

**Tests:** `tests/test_edit_display_polish.py` (~10 cases)

## v5.3.x: Context Intelligence

### Theme

The last experience gap: Claude Code feels like it "knows" your codebase.
It reads the files relevant to your request without you having to list
them. When the context window fills up, it summarises what it already
knows rather than losing it. v5.3.x closes these gaps.

This is the highest-complexity train. It adds semantic context selection
and context compaction, which are both non-trivial but critical for
large-codebase usability.

### Known issues addressed in this train

| ID | Issue |
|---|---|
| C1 | Agent doesn't follow imports; often reads the wrong file first |
| C2 | Context window fills up in long sessions; earlier observations lost |
| C3 | No feedback when context is near the limit |
| C4 | `ContextCollector` keyword selection is weak on unfamiliar codebases |
| C5 | The model re-reads the same files repeatedly in multi-tool turns (wasted tokens) |
| C6 | Agent has no awareness of recent git changes — misses PR context, blame, recent commits |

### v5.3.0 — git-aware-and-import-graph-context

**What:** Two complementary context improvements:

1. **Git-aware context (C6):** inject recent git activity into every session.
2. **Import-graph seeding (C1, C4):** trace imports to pre-load related files.

**Git-aware context (`src/safecode/context/git_context.py`):**

- `GitContextCollector(project_root)`: runs `git log --name-only -30 --format=...`
  (already used in `ContextSelector._recent_files()` for recency bonus — promote
  to a first-class context source).
- `collect_git_context(project_root, task_goal) -> GitContext`:
  - Recent commits (last 10): hash, author, subject, files changed.
  - Files changed since branch diverged from `main`/`master`: `git diff --name-only origin/main...HEAD`.
  - Files with high churn in last 30 days: `git log --format="%H" | git diff-tree`.
  - All wrapped in `subprocess.run([...], shell=False)`, timeout=10s, graceful failure.
- Output injected as a bounded context block (≤ 2000 chars) in `AgentOrchestrator.edit()`.
- Guarded: if git is unavailable or not a git repo, silently skipped.
- **C6 addressed:** agent knows what changed recently, which files are active,
  and can connect user requests to recent git activity without extra `read_file` calls.

**Import-graph context (original plan, unchanged):**

Import-graph-aware context seed for Python, TypeScript/JavaScript,
and Go. When the model starts a task on a file, SafeCode automatically
traces its import graph and suggests the N most relevant related files as
`read_file` calls in the first turn.

**Implementation:**

- New `src/safecode/index/import_graph.py`:
  - Python: parse `import X`, `from X import Y` with `ast.parse` (no
    execution).
  - TypeScript/JS: parse `import ... from '...'`, `require('...')` with
    regex (fast, no TS compiler required).
  - Go: parse `import (...)` blocks with regex.
  - Returns a `ImportGraph` (dict of `path → set[resolved_path]`) built
    lazily; cached in `.sac/index/import_graph.json` with mtime
    invalidation.

- `ContextCollector.collect()` gains an optional `seed_files: list[str]`
  parameter. When provided, the collector resolves each seed file's
  first-degree imports and includes up to `N=5` resolved imports in the
  context (respecting existing budget and sensitive-path guards).

- `AgentOrchestrator.edit()` passes the task's mentioned file paths (if
  any) as `seed_files`. The agent's first turn therefore already has the
  directly-related files in context, reducing redundant `read_file` calls.

**C1 addressed:** agent starts each session with an import-graph-seeded
context rather than just keyword selection.

**C5 partial fix:** with better initial context, the model repeats fewer
redundant reads.

**Tests:** `tests/test_import_graph.py` (~12 cases)
- Python import graph on a multi-file project.
- Circular imports don't loop.
- TypeScript/JS imports.
- Go imports.
- Mtime cache invalidation.
- Budget cap respected (graph traversal stops at N files).
- Sensitive paths excluded from graph output.

### v5.3.1 — context-compaction

**What:** When the accumulated tool-result context in a session would push
the next LLM call over 60% of the context window, trigger compaction: ask
the model to summarise what it has learned so far, then replace the raw
tool results with the compact summary.

**Implementation:**

- New `src/safecode/context/compaction.py`:
  - `ContextCompactor(llm_client, budget: ContextBudget)` class.
  - `should_compact(current_token_estimate: int) -> bool`: returns `True`
    when the estimate exceeds `0.60 * budget.max_tokens`.
  - `compact(observations: list[NativeToolResult]) -> str`: calls the LLM
    with a short "summarise these tool results" prompt. The summary is
    bounded to 2000 tokens by the prompt instructions.
  - The original observations are written to
    `.sac/sessions/<session_id>/observations_compacted_<N>.jsonl`
    (never discarded — only moved out of the live context).

- `AgentLoop` calls `ContextCompactor.should_compact()` before each LLM
  call. On trigger, replaces the observations list in the context with the
  compact summary and appends an audit event `tool_call_compact`.

- **C2 addressed:** long sessions no longer lose context; they compress it.
- **C3 addressed:** the compaction trigger prints a one-line notice to the
  shell: `[Context compacted: 3200 tokens → ~600 token summary]`.

**Cost note:** compaction itself costs one LLM call (the summary prompt).
This is shown in the session cost accumulator as `compaction` with the
token count.

**C5 final fix:** with compaction, the model doesn't need to re-read files
already summarised — the summary includes relevant facts.

**Tests:** `tests/test_context_compaction.py` (~10 cases)
- Compaction triggers at 60% threshold.
- Compaction output is bounded to 2000 tokens (mock).
- Raw observations written to `.sac/sessions/`.
- Compact summary replaces observations in next LLM call.
- Audit event recorded on compaction.
- Two compactions in one session (N=2 file).
- Does not trigger on a fresh session with few observations.

## After v5.3.2: Known Deferred Work

The following are explicitly NOT in this roadmap. They are post-v5.3 work
if the product continues:

- **Computer use / screenshot input:** reading the screen to debug UI.
- **IDE integration:** VS Code extension, JetBrains plugin.
- **RAG / embeddings / vector search:** semantic file retrieval at scale.
- **Multi-repo context:** agent operating across multiple repositories.
- **Remote agents / background tasks:** fire-and-forget long-running tasks.
- **Anthropic MCP server:** exposing SafeCode tools as MCP resources.

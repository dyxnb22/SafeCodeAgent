# SafeCode Agent v4.1 → v4.8 Shell-First Roadmap

Status: planning only. No runtime change in this roadmap pass.
Implementation baseline: tag `v4.0.1`, package version `4.0.1`, branch `main`.
Contract-cut baseline: tag `v4.0.0`.
Companion audit: `docs/archive/audits/commercial-v1-readiness-audit-v3.11.x.md`.
Authoring date: 2026-06-04.

This roadmap supersedes `docs/version-plans/v3.7-to-v4.0-product-roadmap.md`
as the active forward plan. It is **scoped to shell-first functional
completeness**, not commercialization. The previous roadmap closed at
v4.0.0 with the contract cut documented in `docs/public-contracts.md`.

The product target for this train is a local terminal coding agent that a
developer can actually use to: inspect a project, ask questions, edit code,
run tests/build/lint/typecheck, fix failures, approve patches, roll back,
commit locally, resume interrupted work, and understand what happened —
without leaving the terminal and without giving up the v3.0 safety
contracts. The reference points for the *experience* are Claude Code and
similar local terminal agents; SafeCode adds proposal-before-mutation
gates, durable audit, rollback, and a non-permissive default policy.

Throughout this document:

- "Stable contract" means an entry in `docs/public-contracts.md`. There are
  twelve as of v4.0.0.
- "Experimental surface" means new behavior is allowed to change in any
  minor release. New v4.1–v4.8 work is experimental by default.
- "Sidecar" means a state file that **references** stable artifacts (pending
  patch id, audit trace id) without changing their schemas.

---

## 1. Executive summary

Three sentences:

1. v4.0.0 shipped a v3.0-stable safety substrate (patch/checkpoint/audit/
   rollback, command policy, sandbox lifecycle, MCP read execution, JSON
   envelope, LLM provider) but the *daily terminal loop on top of that
   substrate is fragmented*: 27 visible CLI commands, no unified task
   identity, no `sac status`, no test-fix loop, no `sac commit`, no
   `sac resume`, no debug bundle, and project memory split across three
   stores.
2. The v4.1–v4.8 train closes those gaps with **eight focused minor
   releases**, every one of which adds *experimental* surfaces only and
   keeps the v4.0 stable-contract budget at zero new stable promotions.
3. v5.0 is **not** scheduled. No work in this train requires a public
   contract break; if one becomes necessary we reopen v5.0 with a single
   targeted contract change rather than accumulating churn.

Hard non-negotiables for every batch below (identical to v3.7–v4.0):

- Diff review, checkpoint, audit, rollback, command policy, sandbox
  approval, and MCP write proposal gates are not bypassed for convenience.
- Project-local config never lowers user-level safety policy.
- Network and write capabilities default denied.
- Approval stores and audit anchors live outside the project root.
- Default LLM provider stays `mock` in tests.
- No telemetry on by default. No auto-apply by default. No real-network in
  tests.
- No external plugin ABI; no team/SaaS backend; no IDE marketplace claims.

### 2.2 What blocks shell-first daily use today

| Gap | Why it hurts daily use |
|---|---|
| **No unified task identity** | `sac edit` → `sac apply` → `sac rollback` → `sac fix` each touch separate state. Nothing answers "what task am I on, what is its pending patch, what was the last test failure?" |
| **No `sac status`** | User runs `sac history`, `sac config show`, `sac doctor`, and `sac logs show` to reconstruct what would fit in one screen. |
| **`sac fix` is single-shot** | After `sac apply`, nothing re-runs the failing test. No bounded fix loop. No stop-on-no-progress. |
| **No persisted project command profile** | `ProjectTestDetector` re-detects every invocation. No `--suite lint` / `--suite typecheck` / `--suite build`. No override file. |
| **No `sac resume`** | `sac agent resume` exists but is hidden under the experimental `agent` group; the top-level loop has no recovery command. |
| **No budget UX** | Step/time/retry/token budgets exist piecemeal inside `AgentLoop`; user cannot inspect or configure them. |
| **No `sac commit`** | User must manually `git add -p` then write a commit message that doesn't mention the task. Rollback-after-commit has no warning path. |
| **Fragmented memory** | `MemoryStore`, `ProgressState`, `ProjectRules` are three separate APIs with three separate files; no single `sac memory show` view, no pinned-files surface. |
| **No debug bundle** | When something breaks, the user has to copy/paste from four different commands. |
| **No failure taxonomy at runtime** | `LoopFailureCategory` exists in eval, not in runtime. `sac logs show --level error` gives raw tracebacks, not categories or remediation hints. |
| **No workflow-level smoke** | All evidence is unit/contract-level. There is no <60s "the daily loop still works" suite. |
| **CLI sprawl** | 27 visible top-level commands. `audit`, `hooks`, `progress`, `memory`, `queue`, `export`, `tui`, `index`, `subagent`, `skills`, `tools`, `eval` are all in root help. A new user cannot identify the daily-use subset. |
| **Stuck-loop detection** | Loop retry exists for `RecoverableContractFailure` (v2.9.1). There is no detection of "agent proposed the same intent three times in a row." |
| **Ctrl-C recovery** | Interrupting `sac edit` or `sac fix` leaves no resumable marker beyond the journal — which is not surfaced. |
| **Dirty-tree handling** | `sac apply` writes through `git`-unaware paths. Nothing warns the user before clobbering uncommitted unrelated changes. |
| **`sac history` is not task-scoped** | No `--task <id>` filter; recent events bleed across tasks. |

### 2.3 Safe to defer past v4.8

- VS Code / IDE marketplace publishing and VSIX release-cycle evidence.
- PyPI / pipx / brew / signed-public-artifact distribution claims.
- SaaS / team / cloud backends; remote agents; remote PR automation.
- Stable external plugin ABI for `ToolSpec`.
- Stable promotion of sandbox real execution (stays opt-in with preflight).
- Stable promotion of `sac report html`, TUI, IDE JSON-RPC.
- Loop-eval CI blocking; live-provider CI green train evidence.

### 2.4 Most painful gaps (ranked)

1. No unified task identity + no `sac status` (everything else compounds on this).
2. No reliable test-fix loop with bounded retry (current `sac fix` is one shot).
3. No `sac resume` / Ctrl-C recovery / stuck-loop detection.
4. No `sac commit` and no dirty-tree guard.
5. Fragmented memory and no pinned-files surface.
6. No debug bundle and no runtime failure taxonomy.
7. CLI sprawl confuses the daily-use subset.

## 3. Roadmap recommendation: v4.1 → v4.8

Recommended version train. Each minor release is one or two batches sized
for a single Claude Code / Sonnet session and is **strictly additive** —
all new surfaces are labeled experimental on landing.

| Version | Theme | Why this order | What becomes usable after |
|---|---|---|---|
| v4.1 | Unified Task State + `sac status` | Everything else attaches to a task id. Without this, fix-loop / resume / commit / memory have no anchor. | One task identity across ask/edit/fix/apply/rollback/run. `sac status` answers "where am I?" in one screen. |
| v4.2 | Project Command Profile (test/lint/typecheck/build) | Test-fix loop needs a deterministic test command. Profile is also the artifact `sac fix` / `sac run --suite` / `sac commit` will read. | `sac profile detect/show/set/clear`; `sac run --suite test\|lint\|typecheck\|build` through policy; `sac fix` uses profile. |
| v4.3 | Reliable Test-Fix Loop | Profile + task state make the loop expressible. Loop budgets and no-progress detection plug into v4.1. | `sac fix --watch` (still approval-gated apply): bounded iterations, no-progress detection, per-iteration journaling. |
| v4.4 | Resume / Recovery / Budgets | Fix-loop produces interruptible long-running operations. Need to make them safe to interrupt and resume. | `sac resume`, Ctrl-C → durable interrupted state, per-task step/time/retry/token budgets, stuck-loop guard. |
| v4.5 | Local Git Delivery | Tasks need a clean exit path. Resume / dirty-tree handling must be in place first. | `sac commit` (task-aware, dirty-tree guarded), `sac branch new`, rollback-after-commit warning. |
| v4.6 | Project Memory + Rules unification | Memory consumes task state + recent failures from v4.3. Pinning is wired into context selection. | `sac memory show/pin/unpin/clear/add-note`; recent-failures + recent-edits + pinned-files informing context. |
| v4.7 | Debug Bundle + Failure Taxonomy | Once tasks/profiles/memory/git/commit exist, debugging needs a single export. Failure categories from eval extended to runtime. | `sac debug bundle/last-failure`, `sac audit query`, structured failure categories in runtime logs. |
| v4.8 | Workflow Smoke Suite + Docs Cut + CLI Surface Trim | Closes the train. Proves the daily loop works end-to-end. Trims CLI to ≤17 visible commands. Cuts docs to reflect v4.x reality. | `sac smoke shell-first` (<60s), README/MVP guide rewritten around the task-first loop, root help shows only daily-use commands. |

Intentionally deferred through v4.8:

- VS Code / IDE work, PyPI / pipx / brew, signed public artifacts.
- Live-provider blocking CI, loop-eval blocking CI promotion.
- Stable promotion of sandbox real execution, HTML report, TUI, IDE JSON-RPC.
- Auto-apply, auto-commit, auto-push.
- External plugin ABI, MCP write defaulting on.
- Multi-machine task store, remote audit, remote memory.

## 5. Contract strategy

### 5.1 Which v4.0 contracts remain stable

All twelve v4.0.0 stable contracts (`docs/public-contracts.md` sections
1–12) **remain stable and unchanged** through v4.8:

1. Config precedence and lowering rules
2. Pending patch format
3. Audit event hash-chain behavior
4. Sandbox approval and result lifecycle
5. Local tool registry shape
6. Deterministic eval trace format
7. Recommended CLI workflows (extended *additively*: new commands appear,
   no removals or renames)
8. Hidden/internal release command policy
9. LLM provider contract
10. Subagent dispatch payload v2 contract
11. CLI JSON envelope contract
12. MCP read execution contract

### 5.2 What stays experimental through v4.8

All new v4.1–v4.8 surfaces:

- `sac task`, `sac status`, `sac profile`, `sac resume`, `sac commit`,
  `sac branch new`, `sac diff --task`, `sac memory` (unified), `sac debug`,
  `sac audit query`, `sac smoke`.
- `.sac/tasks/`, `.sac/memory/`, `.sac/project_profile.json` file layouts.
- Failure category enumeration in runtime logs.
- Per-task budget configuration.
- `sac fix --watch` behavior.

Already-experimental surfaces unchanged in stability: HTML report, TUI,
IDE JSON-RPC, MCP write execution, sandbox real execution, live-provider
behavior. None promoted in v4.x.

### 5.3 Whether any change should wait for v5.0

**No.** Every batch above is strictly additive against the v4.0 stable
contracts:

- Audit `metadata` is already an opaque `Mapping[str, str]` (stable
  contract 3). Adding a documented `task_id` key inside it does not change
  the field set. The snapshot (`audit_event_schema.json`) verifies
  AuditEvent fields, not metadata keys.
- Pending patch format is unchanged. Task↔patch linkage lives in the
  *sidecar*, not in `PatchProposal`.
- Recommended CLI workflows is a list; adding commands to it is additive.
  No documented command is removed or renamed.

If during implementation a real contract break becomes necessary (e.g., a
new required field in `AuditEvent`), the work for that change opens v5.0
as a focused single-contract release. Do not accumulate breaking changes
for a "big v5.0."

### 5.4 Churn budget

- **v4.x churn budget:** zero new stable contracts promoted through v4.8,
  zero breaking changes to v3.0/v4.0 stable contracts.
- **Experimental-to-stable promotion criteria** (carried from v4.0
  versioning policy): a surface becomes a candidate for stable promotion
  only when (a) docs exist, (b) a snapshot test exists, (c) the surface
  has shipped unchanged across at least three patch releases, (d) at
  least one external user has consumed it in a documented workflow.
  No surface in v4.1–v4.8 will meet (c) until v4.8 + three months, so
  promotion of any v4.x surface is at v5.0 earliest — and v5.0 is not
  scheduled.

## 6. Safety strategy

### 6.1 How the roadmap preserves the v3.0 safety invariants

Every batch is reviewed against the seven hard non-negotiables in
Section 1. Specifically:

| Invariant | How v4.1–v4.8 keeps it |
|---|---|
| Diff review never bypassed | `sac fix --watch` re-invokes the proposal flow; each apply still requires explicit `sac apply`. |
| Checkpoint always before apply | Unchanged. New `sac commit` runs *after* apply, never replaces it. |
| Audit chain always extended | `task_id` is a metadata key only; chain shape unchanged. |
| Rollback always available | `sac rollback --last` preserved; new dirty-tree + post-commit warnings *prevent* unsafe rollback, never bypass it. |
| Command policy enforced | `sac run --suite` and `sac commit`'s `git` calls all go through `ShellRunner`. |
| Sandbox proposal/approval/preflight gates | Untouched in v4.x. Sandbox real execution remains opt-in + preflight-gated; never default. |
| Project config cannot lower user-level safety | Task budgets cannot weaken policy; `sac memory pin` cannot promote a file outside the project root; pinned-files quota cannot evade context redaction. |

### 6.2 Where approvals remain required

- Every `sac apply` continues to require explicit invocation (and modal
  approval where configured). `sac fix --watch` never auto-applies.
- `sac commit --force-uncommit` (the rollback-after-commit override) is
  explicitly dangerous, documented as such, and emits an audit event with
  the commit sha so the action is recoverable.
- `sac branch new` refuses on dirty unrelated tree by default.
- MCP write proposals continue to require approval; no v4.x batch
  weakens this.

### 6.3 Where sandbox / preflight remains relevant

- Sandbox executor preflight (v3.11.2) is the gate for any *opt-in* real
  execution backend. v4.x does **not** promote any backend to default.
  `sac smoke shell-first` runs against Noop only.
- `sac debug bundle` does not execute anything beyond `sac doctor` and
  redacted file reads; it is not a sandbox surface.

### 6.4 What should never become default yet

- Real Docker / Seatbelt / Bubblewrap execution — stay opt-in + preflight-gated.
- Auto-apply (`sac apply --auto`) — not introduced.
- Auto-commit after apply — not introduced. `sac commit` is always explicit.
- Auto-push — not introduced. No git remote operation in v4.x.
- Telemetry — stays opt-in via existing `SAFECODE_METRICS=1` and OTel exporter.
- Live LLM provider in any test/eval lane — `mock` remains the default.

### 6.5 Provider network ≠ shell execution

Network permission for LLM provider and shell execution remain *separate*
config knobs (`sandbox.network_enabled` + `sandbox.network_allowlist` for
shell/MCP; live provider additionally requires the trusted user config
opt-in). v4.x adds no shortcut that conflates them. `sac doctor` reports
both independently; `sac status` surfaces both separately when relevant.

## 9. Planning quality bar — what this roadmap refuses to do

This roadmap is meant to be honest. It deliberately does not:

- Mark documentation work as shipped behavior. Every "docs cut" row is a
  preflight gate, not a feature.
- Invent external evidence. No "marketplace publish," "PyPI green train,"
  "VS Code daily-use evidence," or "live-provider CI win" appears in any
  acceptance row.
- Plan IDE / packaging / distribution work. Those are deferred past v4.8.
- Promote any v4.x surface to stable. The churn budget is zero for the
  entire train.
- Add auto-apply, auto-commit, auto-push, or default real sandbox
  execution. Each remains an explicit user opt-in.
- Weaken redaction at any boundary (context, journal, subagent merge,
  HTML report, debug bundle).
- Introduce telemetry-on-by-default. Existing OTel exporter and
  `.sac/metrics.jsonl` stay opt-in.
- Let project-local config widen user-level safety policy.
- Allow real-network calls or real-provider calls in any test, eval, or
  smoke lane.
- Plan a v5.0 unless a real contract break forces it. If one becomes
  necessary, v5.0 gets a single contract change and no opportunistic
  bundling.

## 10. Acceptance lens summary

After v4.8, a user sitting at a terminal can:

```
sac quickstart                                    # first run
sac task new "add /health to FastAPI app"
sac status                                        # see what's next
sac ask  "where is the FastAPI app entrypoint?"
sac edit "add a GET /health route returning 200"
sac apply
sac fix --watch                                   # bounded fix loop
sac commit                                        # local commit, task summary
sac rollback --last                               # if needed (warns post-commit)
sac resume                                        # after Ctrl-C
sac memory add-note "health route must stay synchronous"
sac debug bundle --task add-health                # if something broke
sac status                                        # done
```

Every line above goes through the v3.0/v4.0 stable safety contracts.
No line in this loop is auto-applied or auto-committed. No line requires
the network. No line requires a real LLM provider. No line requires real
sandbox backend execution. No line requires IDE or remote infrastructure.

That is the shell-first daily loop this roadmap delivers.

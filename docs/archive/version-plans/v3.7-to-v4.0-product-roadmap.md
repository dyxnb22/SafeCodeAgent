# SafeCode Agent v3.7 → v4.0 Product Roadmap

Status: planning only. No runtime change in this roadmap pass.
Baseline: tag `v3.6.6`, package version `3.6.6`, branch `main`.
Companion audit: `docs/archive/audits/commercial-v1-readiness-audit-v3.6.6.md`.
Authoring date: 2026-06-03.

This document is the active forward plan for SafeCode Agent after the
v3.6.6 commercial-v1 *documentation* cut. It supersedes the post-v3.0
sections of `docs/product-commercialization-roadmap.md` for execution
purposes — that document remains the architectural reference and
record of intent.

The roadmap is brutally honest about which v3.6.6 claims are real and
which are scaffolding. Each batch is sized for a single Claude Code /
Sonnet session, minimizes repeated context reading, and carries a
ready-to-use prompt.

---

## 1. Executive summary

Three sentences:

1. v3.6.6 froze documentation and metadata for "commercial v1," but
   distribution, MCP real execution, the VS Code extension, the
   `sac fix` UX, sandbox executor promotion, and performance evidence
   are not actually shipped.
2. The next stage closes those gaps in five focused minor versions
   (v3.7.x–v3.11.x) and one freeze period (v4.0-prep), keeping the v3.0
   safety contracts intact and adding at most two new stable contracts
   at v4.0.
3. v4.0 is reserved for unavoidable public-contract changes and a
   release-readiness re-audit; it is **not** a feature catch-all.

Hard non-negotiables for every batch below:

- Diff review, checkpoint, audit, rollback, policy, and sandbox gates
  are not bypassed for convenience.
- Project-local config never lowers user-level safety policy.
- Network and write capabilities default denied.
- Approval stores and audit anchors stay outside the project root.
- Default LLM provider stays `mock` for tests.
- No telemetry on by default; no auto-write / auto-execute mode.
- No external plugin ABI; no team/SaaS backend.

---

## 2. Current v3.6.6 reality check (one-paragraph version)

`v3.6.6` is *commercial v1 documentation cut*: contracts, threat
model, landing docs, providers doc, OTel exporter, HTML report, and a
publish-CLI scaffold are all in. PyPI publishing has never run, the
"sigstore-signed wheel" is actually a `cosign`/`gpg` detached signature,
no VS Code extension exists outside an in-tree manifest, MCP stdio is
implemented but not wired into the default read-only runner, `sac fix`
and stack-aware quickstart from the original v3.1.x plan never landed,
sandbox real-execution paths exist as `subprocess.run(shell=False, ...)`
but Noop remains the default, the loop-eval CI gate is still advisory,
the live-provider CI lane has no recorded run, and there is no
performance baseline. See `docs/archive/audits/commercial-v1-readiness-audit-v3.6.6.md`
for the per-criterion table.

## 3. v4.0 readiness goals

By the time v4.0 ships, the following must be **true and demonstrable**:

1. A signed wheel is on PyPI; `pipx install safecode-agent` works on
   macOS + Linux; Windows works at smoke level.
2. The signing mechanism named in the threat model and in `sac release
   publish` matches the implementation (either Sigstore is wired, or
   the docs are corrected to "detached cosign/gpg signature" and the
   threat model updated accordingly).
3. `sac doctor` correctly identifies stale installs against PyPI.
4. `sac fix`, stack-aware `sac quickstart`, and `sac setup --wizard`
   ship as documented, with `--json` outputs.
5. MCP read execution is either wired end to end and promoted, or
   explicitly removed from the DoD and labeled deferred.
6. A published VS Code extension consumes `sac api jsonrpc` for the
   daily loop (or the marketplace promise is removed from the DoD).
7. Loop-eval CI is blocking; live-provider CI lane has at least one
   recorded green train.
8. Performance baseline (`sac eval bench`) lives in CI; live-session
   metrics are written to `.sac/metrics.jsonl` opt-in.
9. Three per-stack tutorials (Python, TypeScript, Go) link from
   README.
10. A `docs/versioning-policy.md` page exists; the v4.0 contract churn
    budget (at most two new stable contracts; zero breaking changes to
    v3.0 contracts) is honored.

If any of (1)–(7) cannot be met honestly, the corresponding line in
the DoD must be deleted, not faked.

---

## 4. Deferred / out-of-scope through v4.0

Each item below remains explicitly out of scope.

- Cloud, team, or SaaS backend.
- Centralized policy server; remote trust roots.
- External plugin ABI for `ToolSpec` (intentional through v4.x).
- Telemetry enabled by default. OTel stays opt-in.
- Auto-fix on save, auto-write, or auto-execute as defaults.
- Replacing the v3.0 patch grammar (unified-diff allowed as opt-in
  experimental adapter only).
- Promoting any sandbox backend to *default*. Real execution may be
  promoted to *opt-in*; Noop remains the default recommendation.
- Weakening redaction at the journal/subagent/context boundaries.
- Removing the project-config-cannot-lower-user-policy invariant.
- Signed audit anchors that depend on an external CA.

## 5. Version train overview

| Range | Theme | Batches | Acceptance lens |
|---|---|---|---|
| v3.7.x | Workflow gap closure (skipped v3.1.x UX) | 3 | `sac fix`, stack-aware quickstart, setup wizard, progress, recency, `--json` envelope promotion |
| v3.8.x | MCP hardening (skipped v3.3.x tail) | 3 | Lifecycle, doctor, per-server scopes, read-execution promotion |
| v3.9.x | Real distribution + IDE/TUI maturation | 4 | Sigstore alignment, test-PyPI rehearsal, pipx/brew docs, VS Code extension VSIX |
| v3.10.x | Observability, performance, loop-eval blocking | 3 | `sac eval bench`, `.sac/metrics.jsonl`, loop-eval blocking, live-provider lane required |
| v3.11.x | Policy management + sandbox executor preflight | 3 | Per-dir trust, ephemeral trust, policy diff, sandbox executor opt-in preflight |
| v4.0-prep | Re-audit, contract churn, versioning-policy doc | 2 | Re-run audit, document churn, decide promotions, no new features |
| v4.0.0 | Public contract changes (if any) + readiness re-audit | 1 | At most two new stable contracts; zero breaking changes to v3.0 contracts |

Train ordering rationale:

- v3.7 (UX) precedes everything else because `sac fix` and stack-aware
  quickstart change the demo path used in every later tutorial.
- v3.8 (MCP) precedes v3.9 IDE work because the IDE bridge re-uses the
  MCP transport patterns; promotion criteria must be consistent.
- v3.9 (distribution) precedes v3.10 metrics because metrics
  measurements need a published install path to be representative.
- v3.10 (perf / blocking gates) precedes v3.11 (policy mgmt) so the
  policy churn lands with a stable performance baseline.
- v3.11 (policy + sandbox preflight) precedes v4.0 so any sandbox
  promotion lands inside the contract-change window.

Each batch below is a self-contained Sonnet session prompt. Each prompt
specifies what to read **first** (small set), what to implement, hard
constraints, and exit commands. Prompts avoid asking the agent to do
unrelated discovery; the roadmap and audit do that work upfront.

## 8. Validation and release process per batch

Every batch above follows the same exit discipline:

1. Targeted tests: `PYTHONPATH=src python3 -m pytest <changed_test_files> -q`.
2. Full regression: `PYTHONPATH=src python3 -m pytest -q`.
3. Preflight: `PYTHONPATH=src python3 -m safecode.cli release preflight`.
4. Version bump: `pyproject.toml` + `src/safecode/__init__.py` in lockstep.
5. Version note: `docs/version-notes/vX.Y.Z-*.md` with a heading that mentions the version.
6. Implementation matrix: append rows under the appropriate section.
7. `.claude/skills/current/SKILL.md`: update the "Current Baseline" header and prepend the new section.
8. `.claude/versions.json`: `sac release sync-versions-json` (or manual update of `current_implemented_tag`, `current_local_version`, `latest_tags`, `local_versions`).
9. Commit message: `Implement vX.Y.Z <slug>`. Tag `vX.Y.Z`.
10. Git tag must exactly match `pyproject.toml` and `safecode.__version__`.

No batch is "done" until each of those steps is green.

CI matrix expectations during v3.7.x–v4.0.0:

- Python 3.11/3.12/3.13 × {ubuntu, macos} — required.
- Windows smoke — advisory unless a batch explicitly says otherwise.
- Loop-eval — advisory until v3.10.1 (then blocking).
- Live-provider — advisory throughout v3.x; promotion decision deferred to v4.0+ unless v3.10.1 evidence strongly supports it.

Promotion criteria for any new stable contract (applied at v3.7.2,
v3.8.2, and v4.0.0):

- Snapshot file exists under `tests/snapshots/contracts/`.
- At least one snapshot test enforces it.
- Documentation in `docs/public-contracts.md` is current.
- The corresponding feature has shipped in at least one prior tag and
  has not changed shape across two tags.

## 9. Cross-batch invariants

These hold across every batch. If a batch would violate one, redesign
the batch.

- The eight v3.0 public contracts do not change shape.
- `PatchProposal` / `PatchBlock`, `AuditEvent`, `ToolSpec`,
  sandbox proposal/approval/result, eval trace, config lowering rules
  all keep their snapshots.
- The recommended daily CLI surface (`setup`, `quickstart`, `ask`,
  `edit`, `apply`, `rollback`, `run`, `doctor`, `version`,
  `release preflight/bump/changelog`) keeps its names and argument
  shapes.
- Default LLM provider stays `mock` for tests; live tests live in
  `tests/live/` and remain gated on the `SAFECODE_LIVE_TESTS` env var.
- Network capability defaults denied; provider switching requires
  user-level (not project-local) config.
- Approval atomicity and outside-project trust roots are preserved.
- No telemetry on by default; OTel exporter remains opt-in.
- No external plugin ABI for `ToolSpec`.

## 10. Open decision points to revisit at v3.99.0

- Should `sac report html` become a stable contract? Default: no.
- Should the local patch grammar gain a unified-diff adapter? Default:
  experimental opt-in only.
- Should any sandbox backend become the default after promotion?
  Default: no — Noop stays default; backends are opt-in real-execution.
- Should the loop-eval gate be blocking after v3.10.1? Default: yes,
  conditional on evidence.
- Should the IDE JSON-RPC contract be promoted at v4.0? Default: only
  if T-3.9.2-A actually ships a VSIX and an extension consumes it for
  one release cycle.
- Should `sac fix --auto-apply` exist? Default: **no** through v4.0 —
  approvals stay mandatory.

The v3.99.0 batch must record an explicit decision on each of these,
even if the decision is "defer."

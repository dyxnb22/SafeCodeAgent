# v4.20 → v5.0 Product Roadmap: SafeCode as a Real Coding Agent

## Vision
SafeCode Agent should reach the same tier of utility as Claude Code and
OpenCode — a terminal coding agent the user keeps open all day, that can
explore any codebase, make coordinated multi-file edits, run tests, and
push branches — while retaining its distinguishing safety properties:
per-operation audit log, checkpoint/rollback for every write, and
policy-gated command execution.

The pitch is: **"Claude Code with an audit trail and a kill switch."**

---

## The Core Gap (Current State Analysis)

### What Claude Code / OpenCode do

1. **Native tool calling.** The model is given a JSON schema of available
   tools (`read_file`, `edit_file`, `write_file`, `bash`, `grep`, `glob`,
   `web_fetch`, …). When the model wants to act it emits a native
   function-call object, not freeform JSON. The SDK delivers the call; the
   runtime executes it; the result flows back into the model's context.

2. **Multi-tool turns.** The model can call many tools per user message
   before generating a final response. Reading five files, grepping for a
   symbol, then proposing an edit is a single "turn".

3. **Streaming tool results.** Each tool result appears in the terminal
   immediately; the model sees incremental observations and can adjust.

4. **Arbitrary file read.** The agent can `read_file("src/foo/bar.py")` on
   demand. It is not limited to pre-packaged context.

5. **Provider-native.** Claude Code uses the Anthropic SDK with proper
   tool-use API; OpenCode supports multiple providers natively.

### What SafeCode currently does (v4.18.2 baseline)

- The model emits **custom JSON** (`{"type":"tool_intent","intent":{"type":"read","target":"..."}}`),
  which the loop parses and routes. Only one intent per step.
- **"read" intent** calls `ContextCollector` — a budget-packing context
  summary. The model cannot request an arbitrary file path.
- **"patch" intent** proposes a unified diff for the entire change set.
  Approval is at the patch level, not the file level.
- **"shell" intent** proposes a shell command (approval required).
- There is no `edit_file`, no `grep`, no `glob`, no `web_fetch`.

### The gap in one sentence

SafeCode's agent loop is **one-intent-per-step** and **context-packaged**;
Claude Code's is **multi-tool-per-turn** and **model-driven exploration**.

## Strategy: Incremental Bridge, Not Rewrite

The existing safety infrastructure — checkpoint, audit, policy gate,
rollback — is valuable and must be preserved. The plan adds a **Native Tool
Protocol** layer alongside (then replacing) the JSON-intent layer. Each
tool is either:

- **Auto-approved (read-only):** `read_file`, `list_files`, `search_files`,
  `grep_files` — execute immediately, audited but no checkpoint needed.
- **Approval-gated (write):** `edit_file`, `write_file` — checkpoint
  created before apply, same audit/rollback machinery as today's `sac apply`.
- **Policy-gated (command):** `run_command` — passes through the existing
  shell policy, blocked on high-risk patterns, approved or auto-approved
  per policy level.

## v4.20.x: Native Tool Protocol — Read Side

### Theme
Introduce the native tool calling protocol for safe read-only tools.
The model starts calling real tools (`read_file`, `list_files`,
`search_files`, `grep_files`) instead of the custom JSON intent for reads.
No write tools yet. No approval needed for these four tools.

**Bugs fixed in this train: B4, B5, B17**

### v4.20.0 — native-tool-protocol

**What:** Add a `NativeTool` abstraction and a `NativeToolDispatcher`
alongside the existing `ToolIntentRouter`. Define the wire format:

```json
{
  "type": "native_tool_call",
  "tool_name": "read_file",
  "input": {"path": "src/safecode/cli.py", "lines": [1, 80]}
}
```

**Scope:**
- New `src/safecode/agent/native_tools.py`: `NativeToolSpec` (Pydantic
  schema a tool exposes to the model), `NativeToolCall` (a call from the
  model), `NativeToolResult` (the structured response back).
- New `src/safecode/agent/native_dispatcher.py`: `NativeToolDispatcher`
  that maps `tool_name → NativeToolSpec` and validates inputs.
- `schemas.py` extended with `AgentNativeToolCallResponse` (new union
  member) while keeping all existing response types.
- Existing `ToolIntentRouter` untouched; both protocols coexist.
- The system prompt for the agent gains a `## Available Tools` section
  listing the four read tools with their JSON schemas.

**Bug B4 fix:** Change `TOKEN_CHAR_RATIO` in `context/budget.py` from `4`
to `3.5`. Add a `_CODE_TOKEN_CHAR_RATIO = 3.2` constant for file content
estimation (code is denser than prose). Update `estimate_tokens_from_bytes`
to accept an optional `content_type` hint.

**Bug B5 fix:** When the `max_tree_files` cap fires in
`context/collector.py`, append a metadata entry
`{"truncated": true, "cap": max_tree_files}` to the collector output so the
model and any display layer can see that the tree is incomplete.

**Bug B17 fix:** Add a `max_total_context_bytes` guard in
`ContextBudgetPacker.add()`: when the aggregate selected-context byte total
would exceed the budget cap, stop accepting new sources even if individual
files are under `max_file_bytes`.

**Tests:** `tests/test_native_tool_protocol.py` + additions to
`tests/test_context_budget.py` covering B4/B5/B17 edge cases.

### v4.20.1 — read-tools

**What:** Implement the four read-only native tools and wire them into
`AgentLoop.step()`.

| Tool | Input | Behaviour |
|---|---|---|
| `read_file` | `path: str`, `start_line?: int`, `end_line?: int` | Read a file under project root, up to 400 lines per call. Refuses root escapes. Applies `redact_secrets()` to output. |
| `list_files` | `path?: str` (default: `.`), `recursive?: bool` | List files/dirs under project root. Respects `.gitignore` via existing ignore logic. Returns `truncated: true` when cap reached. |
| `search_files` | `pattern: str`, `path?: str`, `include_glob?: str` | `grep -rn`-like search, returns `{file, line, content}` list capped at 100 results. Uses `safecode.index` file map; no shell out. |
| `grep_files` | `regex: str`, `path?: str`, `case_insensitive?: bool` | Regex variant of `search_files`, same cap, uses `re` module. |

**Safety invariants:**
- All four: path validated against project root (reuse
  `MemoryFacade.normalize_project_path`).
- `read_file`: respects existing `SafeFilters` binary/sensitive-path rules.
- `redact_secrets()` applied to all `read_file` observations.
- Results audited as `tool_call_read` events (lightweight, no checkpoint).
- Read-tool calls do NOT count toward the stuck-loop guard identity.

**Tests:** `tests/test_read_tools.py` (~15 cases)

## v4.21.x: Native Tool Protocol — Write Side

### Theme

**Bugs fixed in this train: B6, B7, B8**

### v4.21.0 — edit-and-write-tools

**What:** Two new write-side native tools.

| Tool | Input | Behaviour |
|---|---|---|
| `edit_file` | `path: str`, `old_string: str`, `new_string: str`, `description?: str` | Exact string replacement in one file. Fails if `old_string` not found or not unique. Creates a checkpoint *before* apply. |
| `write_file` | `path: str`, `content: str`, `description?: str` | Overwrite or create a file. Creates a checkpoint *before* apply. Refuses outside project root or sensitive paths. |

**Bug B6 fix:** `patch/applier.py` add support for `create` (new file,
no prior content check) and `delete` (remove a file, checkpoint records the
deletion) operation types, matching the `PatchBlockOperation` enum. Tests
extended in `tests/test_patch_apply.py`.

**Bug B7 fix:** `patch/applier.py` wraps all filesystem mutations in try/except
for `PermissionError`, `OSError` (ENOSPC = disk full), and platform-specific
file-lock errors. On failure, attempts rollback of already-applied blocks in
the current batch; surfaces a structured `PatchApplyError` with
`failure_reason` field.

**Bug B8 fix:** Change `AgentLoop.run()` default `max_steps` from `5` to
`20`. The existing step-budget default (v4.4.1) remains at 8 per-task; the
loop default now matches realistic task sizes.

**Checkpoint integration:**
- Each `edit_file` / `write_file` call creates a `CheckpointRecord` before
  mutation. Checkpoint id stored in `NativeToolResult` and audit event.
- `ToolCallGate` consulted before every write tool call.

**Approval model:**
- Both tools: `requires_approval: true` in `NativeToolSpec`.
- `AgentLoop` pauses, emits `StopForUserAction` with a Rich diff preview.
- Policy `experimental` may auto-approve `edit_file` on files already read
  in the same session; `balanced` always prompts.

**Tests:** `tests/test_write_tools.py` (~15 cases)

## v4.22.x: Multi-Tool Turns + Agentic Shell

### Theme
Let the model emit and the loop execute **multiple tool calls per user
message** before generating a final response. This is the step that makes
the agent feel like Claude Code: the user types a request, the agent reads
five files, greps for a symbol, edits two files, and reports back — all
in one turn.

**Bugs fixed in this train: B9, B10, B11**

### v4.22.0 — multi-tool-turn

**What:** The agent loop collects a sequence of tool calls in a single
"turn" until the model emits `answer` or `stop_for_user`.

**Protocol:**
- `AgentLoop` accumulates `NativeToolResult` observations and feeds them
  back as a tool-result context block before asking for the next action.
- Per-turn cap: max 20 tool calls; auto-emits `stop_for_user` with hint on
  cap hit.
- Write-tool calls still pause for approval; the turn resumes after approval.

**Bug B9 fix:** Stuck-loop detection (`_abort_if_stuck_tool_intent`)
extended to fire even when `TaskStore.current_id()` returns `None`. When
outside a task, the guard still aborts after 3 identical consecutive
intents and logs a runtime warning; it does not attempt to write a task
sidecar.

**Stuck-loop guard in multi-tool turns:** Identity computed across the
whole turn's tool-call sequence, not per individual call.

**Tests:** `tests/test_multi_tool_turn.py` (~12 cases)

---

### v4.22.1 — shell-session-quality

**What:** UX polish for `sac shell` in the multi-tool era.

- **Bug B10 fix:** `/clear` now calls `AgentSessionStore.clear(project_root)`

- **Bug B11 fix:** `_read_line()` on EOF now prints `\n[exiting shell]`

- `/history` shows current turn's tool calls and observations in a compact

- `/tools` lists available native tools with one-line descriptions.
- Shell prompt: `sac[N]> ` where N is the turn count.
- Streaming: each tool-call name and completion status appear in the

## v4.25.x: Reliability Hardening

### Theme
Before promoting anything to stable, close the remaining reliability and
operational gaps found in the v4.18.2 audit. This train has no new user-
visible features — only fixes, guards, and improved diagnostics.

**Bugs fixed in this train: B13, B14, B15**

### v4.25.0 — checkpoint-integrity

**What:** Add checksum verification to the checkpoint/rollback path.

**Bug B13 fix:**
- `CheckpointManager.create()`: after `shutil.copy2`, compute and store
  `sha256` of every backup file in `CheckpointFileOperation.backup_sha256`.
- `CheckpointManager._restore_checkpoint()`: before `shutil.copy2` on
  restore, verify the backup file's sha256 matches the stored value. If
  mismatch, raise `CheckpointIntegrityError` with the path and hash
  discrepancy — never silently restore a corrupt backup.
- `CheckpointMetadata` model gains optional `backup_sha256: str | None`
  field. Old checkpoints without it skip the check (backward compatible).

**Tests:** `tests/test_checkpoint.py` extended (~5 new cases): corrupt
backup detected, missing sha256 on old checkpoint skips verification,
fresh create+restore round-trip matches.

## Cross-Cutting Principles (all trains)

### Safety invariants that never change
- Every write tool call creates a checkpoint before executing.
- `ToolCallGate` is consulted before every mutating action.
- Project-local config cannot disable checkpoint, audit, or rollback.
- Sensitive-path and root-boundary checks apply to every `path` input.
- `redact_secrets()` applied to every tool result before model context.

### Audit continuity
- New event types are additive to the existing hash-chain log.
- `sac audit query` gains `--type tool_call_read` etc. as valid filters.

### Test strategy
- Every new tool: dedicated `tests/test_<tool_name>_tool.py`.
- Mock provider for all agent-loop tests; no live API calls in CI.
- `PYTHONPATH=src python3 -m pytest -q` must pass at every version tag.

### Provider compatibility
- All tool machinery is provider-agnostic until v4.23.x. During v4.20–v4.22,
  tools work via the prompt-injection path for all providers.

# SafeCode Agent v2.8 to v3.0 Product and Architecture Roadmap

Status: planning revision.
Baseline: `v2.7.9`.
Purpose: replace the mixed planning/product/architecture parts of the Opus draft with a tighter execution roadmap.

## Review Summary

The original draft is directionally good: it keeps post-v3.0 features out, prioritizes honesty in CLI surfaces, and treats typed boundaries as the path to a stable runtime.

The parts that needed correction:

- It treats v3.0 as a broad public contract freeze too early. Current code still has experimental surfaces such as `SafeCodeLocalAPI`, real LLM client behavior, MCP shim behavior, and subagent journal payloads. v3.0 should freeze only the contracts already proven by tests and docs.
- It mixes product planning, architecture migration, bug fixes, and implementation handoff in one list. That makes the roadmap hard to execute and easy to over-scope.
- It creates too many patch releases before v3.0. A single-maintainer cadence should group small correctness fixes where they share one risk profile.
- It names some architecture surfaces as if already public (`LLM client contract`, broad `SafeCodeLocalAPI`, full `ToolSpec registry`) when the safer move is staged stabilization.
- It should put user-facing CLI design first, then internal architecture, then version packaging.

## Product Direction

SafeCode Agent v3.0 should not mean "everything is public API." It should mean:

- The daily CLI workflow is honest and small.
- Safety-critical state formats are versioned or snapshot-tested.
- Internal command sprawl is hidden from ordinary help output.
- Agent behavior has local deterministic evidence before real-provider promises expand.
- Experimental surfaces are explicitly labeled experimental instead of silently treated as stable.

The product promise for v3.0:

> SafeCode Agent is a local, safety-first coding runtime with auditable patch, shell, sandbox, MCP, and subagent boundaries. It is stable enough to build workflows on top of the documented local contracts, but not yet a cloud/team/IDE product.

Non-goals before v3.0:

- Real MCP JSON-RPC client.
- Real concurrent LLM subagents.
- Full TUI rewrite.
- IDE extension.
- Cloud sync or team collaboration.
- Real OpenAI calls in CI.
- New sandbox backend.
- Signed audit anchors.

## Product Surface Design

User-visible CLI should converge around the workflows users actually need:

- `sac quickstart`
- `sac doctor`
- `sac ask`
- `sac agent ...`
- `sac run ...`
- `sac sandbox ...`
- `sac release preflight`
- `sac release bump`
- `sac release changelog`

Internal or advanced release helpers should remain callable for compatibility, but hidden from normal help:

- `sac release signoff`
- `sac release checklist`
- `sac release check`
- `sac release smoke`
- `sac release meta`

Design rule: a command that is not part of the recommended workflow must say so at runtime, in docs, and in help visibility. The CLI should not require users to understand release internals before shipping a safe version.

## Architecture Principles

### 1. Freeze the safety substrate before the product shell

The strongest v3.0 signal is not a new feature. It is making the existing safety substrate predictable:

- config preset and project override rules
- pending patch state
- audit event shape and hash-chain verification
- sandbox proposal, approval, result lifecycle
- tool registry shape
- deterministic eval trace shape

### 2. Use typed boundaries where behavior crosses modules

Typed objects should be introduced where data crosses a boundary:

- diagnostics emitted by doctor/release/security checks
- pending agent actions rendered by CLI
- subagent findings extracted from journals
- MCP tool metadata used for read/write classification
- contract snapshots used by CI

Avoid adding types only to make code look cleaner. Types should reduce ambiguity at runtime boundaries.

### 3. Keep public, supported, and experimental separate

For v3.0, contract status should be explicit:

| Surface | v3.0 status | Notes |
|---|---|---|
| `SafeCodeConfig` | supported | Freeze field set and merge/lowering rules. |
| pending patch JSON | supported | Versioned schema and backward-compatible loading. |
| audit event schema | supported | Freeze hash-chain rules and known event vocabulary. |
| sandbox proposal/approval/result | supported | Freeze status transitions and single-use claim semantics. |
| internal `ToolSpec` registry | supported but local | Snapshot the registry; do not promise external plugin ABI yet. |
| deterministic eval trace | supported for CI | Snapshot typed traces, not prose text. |
| `SafeCodeLocalAPI` | experimental | Keep `ask()` and `report()` documented; add write methods only after CLI contracts are stable. |
| LLM provider protocol | experimental | Keep mock and structured response tests; do not freeze real-provider behavior yet. |
| MCP schema shim | experimental | Static schema metadata is acceptable; real JSON-RPC is post-v3.0. |
| subagent journal payload | evolving | Add version field and tolerant loading; freeze after more adversarial tests. |

### 4. Collapse version count where risk is shared

The original draft creates too many small tags. Small tags are useful, but only when they isolate meaningful risk. For v2.8-v3.0, use these trains:

- v2.8.x: consolidation and CLI honesty.
- v2.9.x: deterministic evidence and contract preparation.
- v3.0.0: documented stable local runtime contracts, no new feature.

## Revised Version Plan

### v2.8.0 - diagnostic-core

Keep.

Goal: add `src/safecode/core/diagnostic.py` with a small `Diagnostic` model, status enum, aggregation, and renderer.

Product reason: diagnostics become consistent across `doctor`, release preflight, and future safety checks.

Architecture boundary: diagnostic creation is pure; CLI rendering is separate.

Acceptance:

- Diagnostic model and renderer exist.
- No behavior change in user-facing commands yet.
- Tests cover aggregation and rendering.

### v2.8.1 - diagnostic-migration-doctor-release

Move before sandbox strategy split.

Goal: migrate doctor and release checks to emit diagnostics internally while preserving CLI output compatibility.

Files:

- `src/safecode/doctor.py`
- `src/safecode/release/check.py`
- `src/safecode/release/smoke.py`
- `src/safecode/release/preflight.py`
- `src/safecode/release/signoff.py`
- `src/safecode/policy/audit.py`

Product reason: users get consistent pass/fail/warn/skip language. Maintainers get one diagnostic substrate.

Acceptance:

- Existing doctor/release tests pass.
- CLI output remains stable unless the plan explicitly updates wording.
- New tests assert diagnostic status aggregation.

### v2.8.2 - sandbox-backend-strategy-split

Keep, but narrow.

Goal: separate sandbox backend selection strategy from backend execution/proposal logic.

Product reason: `sac sandbox status`, `plan`, `propose`, and `execute` should describe the same backend truth.

Architecture boundary: backend capability detection, recommendation, and proposal execution should not live in one CLI module.

Acceptance:

- No command rename.
- Existing sandbox security evals pass.
- The split reduces coupling without changing backend semantics.

### v2.8.3 - agent-loop-typed-actions

Keep.

Goal: replace boolean/string action rendering in `src/safecode/agent/loop.py` with a typed pending-action object that the CLI renders.

Product reason: the agent should stop for user action with precise, machine-readable state.

Architecture boundary: loop decides action; CLI renders action.

Acceptance:

- No more boolean stringification for pending decisions.
- Existing agent loop tests pass.
- New tests cover approval-required, patch-required, and stop-for-user actions.

### v2.8.4 - mcp-shim-schema-prep

Keep, but frame as experimental.

Goal: prepare typed MCP metadata without implementing real JSON-RPC.

Product reason: MCP read/write classification should become explainable when static schema metadata is available.

Architecture boundary: static metadata augments classification; keyword fallback remains.

Acceptance:

- No behavior change when schema metadata is absent.
- Tests prove keyword fallback still works.
- Docs label the shim as experimental.

### v2.8.5 - release-surface-collapse-full

Keep, with one product correction.

Goal: make the recommended release workflow visible and hide internal helpers.

Visible `sac release --help` commands:

- `preflight`
- `bump`
- `changelog`

Hidden but callable:

- `signoff`
- `checklist`
- `check`
- `smoke`
- `meta`

Product reason: the release surface should guide ordinary users toward the supported path and keep compatibility for CI/internal scripts.

Implementation notes:

- `sac release checklist` should behave as a planning helper, not a release gate.
- `sac release signoff` should emit a `RuntimeWarning` and point to `sac release preflight`.
- `docs/install-update.md` should present one main flow.

Acceptance:

- `sac release --help` shows only the three supported commands.
- Hidden commands remain callable.
- Runtime warning appears for deprecated signoff.
- Existing release tests pass.

### v2.8.6 - cli-sandbox-module-split

Keep, but treat as code health, not product milestone.

Goal: split `src/safecode/cli_sandbox.py` while preserving the exact CLI.

Suggested modules:

- `src/safecode/cli_sandbox_status.py`
- `src/safecode/cli_sandbox_proposal.py`
- `src/safecode/cli_sandbox_executions.py`
- `src/safecode/cli_sandbox.py` keeps the Typer app and registration.

Architecture rule: split by command ownership, not by helper type.

Acceptance:

- No command rename or argument reorder.
- `sac sandbox --help` remains compatible.
- Each new command module stays below roughly 320 LOC.
- Existing sandbox tests pass.

### v2.8.7 - subagent-finding-redaction-at-journal-boundary

Keep, but rename from "merge boundary" to "journal boundary".

Goal: redact secrets when converting journal events to `SubagentFinding`, before merged context reaches agent loop prompts.

Files:

- `src/safecode/subagents/journal_adapter.py`
- `src/safecode/subagents/merge_policy.py`
- `src/safecode/agent/loop.py`
- `tests/test_subagent_redaction.py`
- `tests/test_subagent_orchestration.py`

Architecture rule: producer-side redaction is primary; consumer-side redaction remains defense in depth.

Acceptance:

- Secret-like strings in `summary`, `observations`, and `errors` become `[REDACTED]`.
- Merge remains idempotent under already-redacted input.
- Agent loop logs a warning if consumer-side redaction still changes merged text.

### v2.8.8 - shell-exit-code-honesty

Keep.

Goal: `sac run` returns real policy/approval exit codes.

Product reason: shell users and scripts must be able to trust exit status.

Compatibility:

- Add `SAFECODE_RUN_LEGACY_EXIT_CODE=1` for one minor train only.
- Document the opt-out in `docs/install-update.md`.

Acceptance:

- policy blocked returns 126.
- approval required returns 125.
- legacy env opt-out returns old behavior.

### v2.8.9 - audit-and-hook-event-dedup

Keep.

Goal: prevent skipped hooks from producing duplicate `hook_approval_required` audit events.

Product reason: downstream audit consumers should not double-count one event.

Architecture rule: add `hook_skipped_by_policy` as an additive event type; never rewrite old logs.

Acceptance:

- A skipped hook emits distinct event types.
- Audit chain verification remains backward compatible.

## v2.9 Evidence and Contract Preparation

v2.9 should prove behavior before v3.0 freezes it. The emphasis is deterministic local evidence, not new product surfaces.

### v2.9.0 - agent-loop-fixture-expansion

Keep.

Goal: expand loop fixtures from two to six realistic local scenarios.

Acceptance:

- `sac eval --mode loop` runs all six fixtures locally.
- No real provider calls.
- Failures report typed reason categories.

### v2.9.1 - agent-loop-error-recovery

Keep, but bounded.

Goal: add one bounded retry for transient structured-response failures.

Architecture rule: retry only contract-shaped failures that are explicitly recoverable. Do not retry policy blocks, validation failures, or user-stop states.

Acceptance:

- A scripted first-fail second-pass fixture succeeds.
- Journal records retry event and reason.

### v2.9.2 - eval-replay-baseline-snapshot

Keep.

Goal: snapshot deterministic typed traces for loop evals.

Design rule: snapshot tool intents, event types, status transitions, and diff hashes. Do not snapshot LLM prose.

### v2.9.3 - eval-loop-mode-ci-gate

Keep, but make it advisory first.

Goal: add loop eval to CI as a separate job.

Acceptance:

- CI shows loop eval output.
- It can be advisory initially, then blocking after one clean cycle.

### v2.9.4 - mcp-tools-list-schema-shim

Keep, still experimental.

Goal: classify MCP tools using static schema metadata when present.

Architecture rule: schema metadata lives alongside MCP config and is optional. Absent schema means current keyword classifier behavior remains.

Acceptance:

- Declared write tools are classified as write even without write-like names.
- Unknown bucket shrinks when metadata exists.
- No real JSON-RPC client.

### v2.9.5 - mcp-call-schema-arg-validation

Keep.

Goal: validate call/proposal arguments when schema metadata exists.

Acceptance:

- Extra arguments are rejected when schema forbids them.
- Existing schema-less workloads still pass.

### v2.9.6 - subagent-journal-payload-versioning

Modify from "typed event schema".

Goal: add versioned, tolerant journal payload parsing for subagent dispatch events.

Architecture rule: old journals must load without migration; new journals include payload version.

Acceptance:

- Old v2.7-style journal events parse.
- New events round-trip through typed parsing.
- Invalid payloads are skipped with audit/log evidence, not crashes.

### v2.9.7 - subagent-merge-adversarial-tests

Fold into v2.9.6 unless it grows.

Goal: add adversarial merge tests for duplicate IDs, conflicting observations, near-secret content, malformed payloads, and blocked tasks.

Decision: if this is only tests, include it in v2.9.6. Split only if it reveals behavior changes.

### v2.9.8 - tool-spec-registry-versioning

Keep, but local.

Goal: add versioning to `ToolSpec` and snapshot the local registry.

Architecture rule: this is a local runtime contract, not an external plugin ABI.

Acceptance:

- Every `ToolSpec` has a version.
- Snapshot test protects public local tool names and permission categories.
- Existing tool names do not change.

### v2.9.9 - public-contract-snapshot-tests

Keep, but narrow to v3.0-supported surfaces.

Snapshot targets:

- `SafeCodeConfig`
- pending patch JSON schema
- audit event schema and known event vocabulary
- sandbox proposal/approval/result schemas
- local `ToolSpec` registry listing
- deterministic eval trace shape

Do not snapshot as stable:

- full `SafeCodeLocalAPI`
- real-provider LLM behavior
- MCP JSON-RPC behavior
- subagent concurrent execution behavior

## v3.0.0 Product Definition

Theme: stable local safety runtime. No new feature.

v3.0 freezes:

- documented config precedence and lowering rules
- pending patch format
- audit event hash-chain behavior
- sandbox approval/result lifecycle
- local tool registry shape
- deterministic eval trace format
- recommended CLI workflows and hidden/internal command policy

v3.0 labels as experimental:

- `SafeCodeLocalAPI` beyond `ask()` and `report()`
- OpenAI-compatible live provider behavior
- MCP schema shim
- subagent payload evolution beyond read-only bounded findings
- TUI and IDE surfaces

v3.0 acceptance:

- `docs/public-contracts.md` exists and is linked from README.
- Every supported contract has a snapshot or compatibility test.
- Every experimental surface is labeled in docs.
- `sac --help` and `sac release --help` show only supported daily workflows.
- Full `PYTHONPATH=src python3 -m pytest -q` passes.
- Loop eval and contract snapshot suite pass.

# v5.6 → v5.8 Product Roadmap: Agent Quality, Security, and Cost

## Context

After v5.5.2, SafeCode Agent has a production-grade release path through
PyPI/pipx and is **architecturally complete** (trust modes, context
intelligence, MCP, display). Homebrew work remains evidence that the package
can be formula-ready, but Homebrew is not a required release channel for the
portfolio cut.
The v5.6–v5.8 trains close the remaining quality, security, and operational
gaps that separate a "feature complete" tool from one that is genuinely
reliable in daily use.

| Gap | Symptom | Train |
|---|---|---|
| System prompt is 5 lines | Agent quality ceiling is the prompt, not the architecture | v5.6.x Agent Quality |
| No real-provider eval | Don't know if prompt changes actually help | v5.6.x Agent Quality |
| No golden demo artifact | Hard to evaluate the product quickly from a resume or interview | v5.6.x Agent Quality |
| Subagents idle | Parallel task decomposition unused in shell | v5.7.x Security + Depth |
| Threat model review overdue | Scheduled 2026-12-01; not in any roadmap | v5.7.x Security |
| Sandbox real-exec still deferred | Deferred at v3.x, v4.x, v5.x — needs a final decision | v5.7.x Security |
| No cost caps or alerts | Users can accidentally spend $10 in one session | v5.8.x Cost |
| v6.0 contract cut unplanned | v5.1–v5.5 added new surfaces with no promotion path | v5.8.x → v6.0 |

---

## v5.6.x: Agent Quality

### Theme

The single highest-impact improvement available is the system prompt.
`src/safecode/agent/prompts.py` currently has 5 lines. Claude Code's
equivalent has hundreds of lines of task-specific, failure-specific, and
tool-usage-specific instructions built up over thousands of real sessions.

The gap is not architectural — the tools, the loop, and the context machinery
are all in place. The gap is **what the model is told to do with them**.

v5.6.x addresses this in three steps:
1. Clean up the portfolio-facing release hygiene and rewrite the system prompt.
2. Measure the impact with real-provider evals.
3. Produce a golden demo artifact that proves the task-to-tested-commit loop.

### v5.6.0 — prompt-engineering-and-hygiene

**What:** A substantially improved `SYSTEM_PROMPT` in
`src/safecode/agent/prompts.py`, plus small portfolio-release hygiene commits
that make the project read like a complete open-source artifact.

**Pre-prompt hygiene work:**
- Keep PyPI/pipx as the only required production install path.
- Remove or downgrade Homebrew language from current-status docs so it is not
  presented as a maintained release channel.
- Add root-level project hygiene files: `LICENSE`, `SECURITY.md`,
  `CONTRIBUTING.md`, and `CHANGELOG.md`.
- Fix stale docs language that still points at old v4.18/v5.5/Homebrew
  baselines.
- Make the README's first screen portfolio-ready: what the agent does, the
  safety loop, and the fastest reproducible demo command.

**Target prompt sections:**

```
## Role and constraints
## Tool use strategy
## How to approach a coding task
## How to handle test failures
## How to avoid redundant reads
## When to stop and ask the user
## Patch format rules (for legacy patch path)
## Safety rules (never bypass approval, never expose secrets)
```

**Key behavioural rules to encode:**

**Tool use strategy:**
- Before reading a file, check whether you already have its content from
  an earlier tool call in this turn.
- When searching for a symbol, prefer `search_files` over `read_file` on
  every file in a directory.
- After `edit_file`, do not `read_file` the same path again to verify —
  trust the edit succeeded unless an error was returned.
- If the user's goal mentions a test file or test command, read the test
  file first, then the implementation.

**Task decomposition:**
- Break tasks into: (1) understand the current state, (2) identify exactly
  what needs to change, (3) make the change, (4) verify with a test if
  available. Announce each phase as a one-line status before tool calls.
- For multi-file tasks, read all relevant files in a single turn before
  making any edits.

**Test failure handling:**
- When `run_command` returns a non-zero exit code, read the full error
  output before proposing a fix.
- Do not propose the same fix twice. If a fix didn't work, re-read the
  error and try a different approach.
- If a test still fails after two attempts, stop and ask the user.

**Stopping conditions:**
- Stop and emit `stop_for_user` when: (a) you need a credential the user
  hasn't provided, (b) you've made two failed attempts at the same
  sub-task, (c) the task requires deleting more than one file.
- Never invent file contents. If you don't know what a file contains,
  read it first.

**Safety rules (always in force regardless of trust mode):**
- Never read files matching `.env`, `*secret*`, `*credential*`, `*key*`
  unless the user has explicitly named the file in their request.
- Never include API keys, tokens, or passwords in tool inputs or outputs.
- Do not propose patches to audit, checkpoint, or policy files.

**Implementation notes:**
- `SYSTEM_PROMPT` stays in `src/safecode/agent/prompts.py` as a module
  constant (unchanged interface).
- Add `TOOL_USE_PROMPT_SECTION` helper: injected when native tools are
  active (supplements the dispatcher's `system_prompt_section()`).
- Add `PATCH_FORMAT_PROMPT_SECTION`: injected for legacy patch path only.
- All tests that hard-code `SYSTEM_PROMPT` content must be updated.

**Tests:** `tests/test_system_prompt.py` (~10 cases)
- Prompt contains each required section heading.
- `SYSTEM_PROMPT` is non-empty and longer than 500 chars.
- Tool use strategy section contains "redundant reads" rule.
- Safety section present.
- `TOOL_USE_PROMPT_SECTION` is non-empty and importable.
- Neither prompt section contains hard-coded file paths or version numbers
  (would create maintenance burden).
- `tests/test_project_docs.py` verifies root hygiene files and current docs
  no longer present Homebrew as a required production channel.

### v5.6.1 — real-eval

**What:** Loop eval that works with real LLM providers, producing
measurable quality metrics that can detect prompt regressions.

**Current state:** `sac eval --mode bench` uses `ScriptedLLMClient` only.
It proves the loop architecture is correct but cannot measure prompt quality
or model-specific behaviour.

**New eval mode: `sac eval --mode live`**

```bash
SAFECODE_LIVE_TESTS=1 sac eval --mode live --provider anthropic --fixture python-function-fix
```

**Fixture format extension:**
- `LiveEvalFixture(name, setup_files, goal, success_condition, max_turns)`:
  - `setup_files`: dict of `path → content` to write into a temp project.
  - `goal`: natural-language task goal.
  - `success_condition`: callable `(project_root: Path) -> bool` that checks
    the outcome (e.g., test passes, file contains a string).
  - `max_turns`: cap on agent loop iterations.

**Default live fixtures (5):**
1. `python-add-function`: add a pure function, verify with assert.
2. `python-fix-failing-test`: one broken test → fix it.
3. `python-refactor-rename`: rename a function used in 3 files.
4. `go-add-handler`: add an HTTP handler to a minimal Go server.
5. `ts-fix-type-error`: fix a TypeScript type error.

**Metrics collected per fixture:**
- `success: bool` (did `success_condition` pass?)
- `turns_used: int`
- `tool_calls: int` (total across turns)
- `redundant_reads: int` (same file read twice in one session)
- `input_tokens: int`, `output_tokens: int`
- `wall_seconds: float`

**CI integration:**
- New advisory `live-eval` CI job (like `live-provider`, gated by
  `vars.ENABLE_LIVE_LLM_TESTS`).
- Writes results to `tests/snapshots/live_eval/latest.json`.
- `tests/test_live_eval_baseline.py`: fails if `success` drops below
  previous baseline for any fixture (ratchet — can only improve, never
  regress below a passing baseline).

**Required local evidence:**
- After the mock-tested harness lands, run at least one real provider eval
  locally with a real Anthropic or OpenAI key.
- Store a redacted result artifact under `docs/demo/live-eval-latest.json`
  or `docs/demo/live-eval-summary.md`.
- The artifact must include fixture names, success flags, turns, tool calls,
  token counts, and wall time, with no API keys or raw secret-bearing output.
- This evidence becomes interview/demo material; a mock-only implementation
  does not satisfy v5.6.1.

**Why this matters:** without live eval, prompt changes in v5.6.0 are
unjustified faith. With it, every future prompt or context change can be
measured against a baseline.

**Tests:** `tests/test_live_eval_mode.py` (~8 cases, all using mock)
- Fixture format validates (non-live test).
- `--mode live` without `SAFECODE_LIVE_TESTS=1` skips gracefully.
- Results JSON structure matches schema.
- Ratchet logic: lower success than baseline triggers failure.
- CI job config verified via `tests/test_ci_live_lane.py` extension.
- Project docs link to the redacted live-eval result artifact.

### v5.6.2 — golden-demo-project

**What:** A portfolio-grade, reproducible demo that shows the full SafeCode
loop from bug report to tested local commit.

**Why:** For a resume project, a complete recorded transcript is more valuable
than another hidden runtime feature. The demo is the fastest way for an
interviewer to understand what was built and why it is technically credible.

**Demo story:**
1. Start from a small but real broken project.
2. User gives a bug report or feature request.
3. SafeCode gathers context, proposes a patch, and shows a diff preview.
4. User approves the write.
5. SafeCode applies with checkpoint + audit log.
6. SafeCode runs the relevant test.
7. Test passes.
8. SafeCode offers or creates a local commit.
9. Transcript includes rollback evidence or explains how rollback would work.

**Implementation:**
- Add or refresh `examples/golden-demo/` with a deterministic broken task.
- Add `examples/golden-demo/demo/run-demo.sh` for the mock/no-key path.
- Add `examples/golden-demo/demo/expected-transcript.md`.
- Add an optional asciinema recording or terminal GIF reference under
  `docs/demo/`.
- README links the demo from the first screen.
- `docs/demo/portfolio-demo.md` explains the scenario, commands, expected
  output, safety gates, and how to re-run it.

**Tests:** `tests/test_golden_demo.py` (~8 cases)
- Demo script exists and is executable.
- Demo fixture starts failing and ends passing.
- Expected transcript contains diff preview, checkpoint, audit, test pass,
  and commit/rollback language.
- README and docs index link to the demo.

### v5.7.0 — threat-model-review-and-subagents

**What:** Semi-annual security review of `docs/security/threat-model-v3.6.md`,
updating it to the v5.x surface, plus activation of the idle subagent
infrastructure for parallel read-only analysis. Scheduled review date:
**2026-12-01**.

**Scope of review:**

1. **New execution surfaces since v4.23 (last major addendum):**
   - Trust modes (`--auto-edit`, `--full-auto`): model output can now write
     files without per-file user confirmation. The 10-file guard and session
     rollback are the mitigations. Document the threat and confirm mitigations.
   - Parallel subagents (v5.7.0): race conditions between concurrent write
     tool calls are blocked by serialisation invariant. Confirm the invariant
     holds and add to threat model.
   - MCP write execution (v5.4.1): MCP server output feeds directly into
     `execute_granted_write`. Server could return adversarial content.
     Classification gate is the mitigation. Document.
   - Git-aware context (v5.3.0): `git log` output injected into model context.
     A crafted commit message could attempt prompt injection. Document the
     threat; confirm `redact_secrets()` and bounded context block size.

2. **Existing threats that need evidence update:**
   - Prompt injection via tool results: now that the agent reads arbitrary
     files, the attack surface is larger. Document the `redact_secrets()`
     depth and its limitations.
   - Native tool path validation: verify the root-boundary check is applied
     consistently across all 7 promoted tools + MCP bridge.

3. **Review cadence update:** next scheduled review moves to **2027-06-01**.

**Output:** Updated `docs/security/threat-model-v3.6.md` with:
- A dated "v5.7.0 Review" section.
- Mitigations for each new surface.
- An updated review log row.

**Tests:** `tests/test_threat_model_docs.py` extended:
- Verify review log has a 2026-12-01 entry.
- Verify each new surface (trust modes, subagents, MCP write, git context)
  has a named section in the threat model.
- Verify the next scheduled review date is updated.

**Subagent activation scope:**
- `MultiToolTurnRunner.dispatch_parallel(calls: list[NativeToolCall], *, max_workers: int = 3) -> list[NativeToolResult]`:
  Uses `ThreadPoolExecutor` (already in `SubagentPool`) to dispatch up to
  `max_workers` tool calls in parallel. Read-only tools only; write tools
  always serialised.
- `AgentLoop` heuristic: when a turn's initial calls are all read-only and
  there are ≥ 3 of them, route through `dispatch_parallel`. Otherwise, use
  the existing serial `dispatch_calls`.
- `SubagentSynthesis.synthesize_findings()` called at turn end to merge
  parallel results into a compact summary before feeding back to the model.
- `/parallel-reads` in `sac shell`: shows how many parallel read dispatches
  have fired in the current session.

**Subagent safety invariants:**
- Write tools (`edit_file`, `write_file`, `run_command`) are never
  dispatched in parallel — always serialised with user approval between them.
- `CancellationToken` propagated from session Ctrl-C to all parallel workers.
- Per-tool `redact_secrets()` still applied to each result individually.
- Parallel tool results merged with stable ordering (alphabetical by
  `tool_name + call_id`) for deterministic audit logs.

**Subagent tests:** `tests/test_subagent_activation.py` (~10 cases)
- Parallel dispatch fires for 3+ read-only calls.
- Write calls never dispatched in parallel.
- Cancellation stops all workers.
- Results ordering is stable.
- `dispatch_parallel` errors in one worker don't crash others.

### v5.7.1 — sandbox-and-observability-decisions

**What:** Make the two long-deferred promotion decisions.

**Decision 1: Sandbox real-execution**

The `SandboxExecutorPreflight` (v3.11.2) requires:
- A passing preflight record.
- An explicit env var (`SAFECODE_SANDBOX_DOCKER=1` etc.).

Evidence gathered since v3.11.2 (local tests, CI matrix): Docker backend
works reliably on macOS and ubuntu-latest. Seatbelt (macOS) works. Bubblewrap
(Linux) works in the CI container.

**Decision options:**
- **A (Promote to stable):** `SandboxExecutionProposal` / `SandboxApproval`
  / `SandboxResultRecord` promoted to stable contract. Env gates remain.
  `docs/public-contracts.md` section 17 added.
- **B (Freeze EXPERIMENTAL):** Explicitly mark "will not be promoted before
  v6.0 without new evidence". Add `frozen_experimental` annotation.

Recommendation: **A (Promote)** — the preflight + env gate combination
gives enough safety evidence. The Noop default ensures no accidental
real execution.

**Decision 2: OTel exporter and HTML session report**

Both implemented since v3.6.x:
- `OtelExporter` (v3.6.2): disabled by default; `SAFECODE_OTEL_EXPORTER` env opt-in.
- `SessionHtmlReport` (v3.6.3): `sac report html --session <id>`.

**Decision options:**
- **Promote:** Add contracts for the OTel event schema and HTML report path.
- **Freeze EXPERIMENTAL:** The schema has changed without versioning; users
  who depend on it have no contract. Freeze until a stable schema is defined.

Recommendation: **Freeze both** with explicit documentation. OTel event
schema should be versioned before promotion. HTML report is generated output,
not a stable API.

**Output:**
- `docs/public-contracts.md` updated with sandbox section (if A) and
  frozen EXPERIMENTAL notices for OTel/HTML.
- `tests/test_public_contract_snapshots.py` extended.
- `docs/versioning-policy.md` changelog entry.

### v5.8.0 — cost-guardrails

**What:** Per-project token budget caps and session cost alerts.

**Token budget cap** (new config key `cost.max_tokens_per_session`):
- Stored in project config (`.sac/config.toml`), not user config, because
  it's project-specific.
- Project config **can** lower the cap but **cannot** raise it above the
  user-level cap (same lowering-only rule as policy).
- Default: `unlimited` (no cap).
- When the session token count reaches 90% of the cap, print a yellow
  warning: `"Warning: 90% of session token budget used (18k/20k tokens)."`
- When the cap is hit, emit `stop_for_user` with reason `"budget_exceeded"`;
  the user can choose to continue (which temporarily raises the cap by 10%)
  or end the session.

**Provider cost fallback** (new config key `cost.fallback_on_usd`):
- When estimated session cost exceeds `fallback_on_usd`, switch to
  `fallback_provider` (if configured in `LLMConfig.fallback_provider`).
- Logs a yellow notice: `"Cost threshold reached. Switching to fallback provider."`
- Default: `null` (disabled).

**`/budget` in `sac shell`:** shows current session token count, estimated
cost, and cap (if set).

**Tests:** `tests/test_cost_guardrails.py` (~10 cases)
- Cap warning fires at 90%.
- Stop fires at 100%.
- Continuing after stop adds 10% extension.
- Project config can lower but not raise cap.
- Provider fallback switches on threshold.
- `/budget` output format.

## Items Explicitly NOT in This Roadmap

| Item | Reason |
|---|---|
| RAG / embeddings | Import graph + git context covers the common case; vector DB adds infra complexity |
| Computer use / screenshot | Requires multimodal model API + screen permission model |
| Multi-repo context | Cross-repo path validation redesign needed |
| Remote / background agents | Requires server infrastructure |
| JetBrains / VS Code plugin | Terminal-only scope decision (v5.4 roadmap) |
| Prompt fine-tuning | Model-specific; not platform work |

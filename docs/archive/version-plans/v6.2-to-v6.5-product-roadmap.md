# v6.2 → v6.5 Product Roadmap: Memory, Semantic Retrieval, GitHub Closure, Eval

## Context

SafeCode Agent v6.1.0 is the current baseline. The safety substrate (19 stable
contracts, audit chain, checkpoint/rollback, policy gates, MCP approval) is
complete. The v6.1.0 portfolio cut added live eval evidence, a realistic
multi-file demo, project hooks, and diagnostics-aware context.

This roadmap closes four remaining product gaps in order of priority:

| Gap | Symptom | Train |
|---|---|---|
| No cross-session memory | Agent starts from zero on every session; project conventions re-discovered each time | v6.2.x Memory |
| Context collection is rule-driven only | No semantic retrieval; "find all auth code" depends on keyword match | v6.3.x Semantic Retrieval |
| GitHub workflow still EXPERIMENTAL | Coding agent product loop is incomplete without a stable PR workflow | v6.4.x GitHub Closure |
| Live eval is 2 self-written fixtures | Unverifiable against any public benchmark; hard to answer "how does it compare?" | v6.5.x Eval Alignment |

Non-goals for this roadmap:
- Transactional multi-file patch (deferred; checkpoint provides near-equivalent safety net)
- Full SWE-bench automation at scale (deferred; harness compatibility is enough)
- Remote embedding services (local-only, no API key required)
- IDE extension or TUI rewrite
- New sandbox backends

## v6.2.x: Cross-Session Project Memory (2–3 versions)

### Theme

`sac memory` currently requires the user to manually write key-value facts
(`sac memory test_command "pytest -q"`). The agent does not observe and retain
project conventions on its own. Every session starts with no awareness of what
was done before.

The goal is automatic session summarisation and project-convention detection,
with the same audit discipline that applies to every other write surface.

---

### v6.2.0 — auto-record-session-summary

**What:** At the end of every agent session, write a summary record to
`.sac/memory/sessions.jsonl`. Load the most recent N summaries at session
start and inject them into the context window.

**Key behaviors:**
- Records: touched files, commands run, tests passed/failed, approval decisions
- `sac memory inspect` — human-readable view of stored summaries
- `sac memory clear [--before <date>]` — remove old summaries
- `sac memory export [--out <path>]` — JSON dump for portability
- Summary injection is bounded (token budget cap, same rules as context collector)
- Storage location: `.sac/memory/` (outside project root read-path, consistent
  with audit anchor and approval store conventions)

**Files:**
- `src/safecode/memory/session_store.py` — new
- `src/safecode/memory/summary.py` — new (summariser, token-bounded)
- `src/safecode/agent/orchestrator.py` — write summary on session end
- `src/safecode/agent/loop.py` — inject recent summaries at session start
- `src/safecode/cli_memory.py` — `inspect`, `clear`, `export` subcommands

**Tests:** `tests/test_memory_session_store.py` (20+ tests)

---

### v6.2.1 — project-convention-detection

**What:** The agent automatically extracts project conventions during a session
(test command, guarded directories, discovered API constraints, user-approved
patterns) and writes them to `.sac/memory/project.md` as human-readable facts.

Facts require explicit approval before being persisted as authoritative — they
cannot be injected silently by project-controlled files.

**Key behaviors:**
- `sac memory approve-fact <fact-id>` — approve a pending fact into project.md
- `sac memory list-facts [--pending|--approved]`
- Approved facts are prepended to system prompt on next session
- Project-local files cannot write facts directly (same trust rule as config)
- Approved facts are audit-logged (MemoryFactApprovedEvent)

**Files:**
- `src/safecode/memory/facts.py` — new
- `src/safecode/audit/models.py` — new event type `memory_fact_approved`
- `src/safecode/cli_memory.py` — `approve-fact`, `list-facts` subcommands

**Tests:** `tests/test_memory_facts.py` (15+ tests)

---

### v6.2.2 — memory-docs-and-stable-contract-candidate

## v6.3.x: Semantic Retrieval MVP (3 versions)

### Theme

The current context collector is rule-driven: import graph, git recency,
symbol index, keyword match. This works well for small, familiar codebases but
fails on questions like "find all places that handle token expiry" when the
relevant code does not share keywords with the query.

The goal is a **hybrid retrieval pipeline** — keyword + semantic — with
auditable file selection, local-only embedding (no API key required), and a
safe fallback when the embedding index is unavailable.

The key interview-ready narrative:

> SafeCode combines symbolic context, git recency, and semantic retrieval into
> a hybrid context collector with deterministic fallback and auditable file
> selection reasons.

---

### v6.3.0 — chunking-and-local-embedding-index

**What:** Add a chunking layer on top of `FileIndexer` and build a local
embedding index stored in SQLite.

**Key behaviors:**
- Default embedding backend: `sentence-transformers` (local, CPU-safe)
- If `sentence-transformers` is not installed: auto-fallback to keyword-only
- Index stored in `.sac/index/embeddings.db` (SQLite)
- `sac index build [--force]` — build or rebuild the embedding index
- `sac index status` — show index stats (files, chunks, last built)
- Index is invalidated on file modification (hash-checked)

**Files:**
- `src/safecode/index/chunker.py` — new
- `src/safecode/index/embedding_store.py` — new (sqlite backend)
- `src/safecode/index/embedding_backend.py` — new (pluggable, SentenceTransformer + fallback)
- `src/safecode/cli_index.py` — `build`, `status` subcommands (update existing)

**Tests:** `tests/test_index_embedding.py` (20+ tests; mock backend for CI)

---

### v6.3.1 — hybrid-retrieval-pipeline

**What:** Replace the single-strategy context selector with a hybrid pipeline
that combines BM25 keyword, semantic embedding, git recency, and import graph
scores. Every selected file carries a `selection_reason` explaining why it was
chosen.

**Key behaviors:**
- `ContextSelector.select()` returns `ContextFile` objects with `selection_reason`
  field: one of `keyword`, `semantic`, `import_graph`, `git_recency`, or `pinned`
- `sac search "<query>"` — standalone semantic search command, outputs ranked
  files with reasons
- Hybrid weights are configurable in user config (`context.semantic_weight`,
  default 0.3); project config can only lower weight, never raise above user value
- Fallback chain: semantic → keyword-only → import graph only

**Files:**
- `src/safecode/context/hybrid_retrieval.py` — new
- `src/safecode/context/selector.py` — updated to use hybrid pipeline
- `src/safecode/agent/schemas.py` — `ContextFile.selection_reason` field
- `src/safecode/cli.py` — `sac search` command

**Tests:** `tests/test_context_hybrid_retrieval.py` (25+ tests)

## v6.4.x: GitHub PR Workflow Stable Contract (1–2 versions)

### Theme

`github_create_pr` and `github_push_branch` exist but are EXPERIMENTAL. A
coding agent that cannot reliably close the `edit → apply → PR` loop is
incomplete as a product. This train promotes the GitHub workflow to a stable
contract with structural safety guarantees.

---

### v6.4.0 — github-pr-stable-contract

**What:** Promote `github_create_pr` and `github_push_branch` to stable
contract (Section 20/21 of public-contracts.md).

**Stable invariants:**
- Structural block on pushing to `main` or `master` (not just a documentation
  note — ToolCallGate rejects the call before execution)
- PR body always includes: diff summary, checkpoint ID, audit event reference
- Approval gate: PR preview shown before push; user must confirm
- Failure leaves local state intact (no partial push without rollback)
- `--dry-run` flag available for all GitHub write operations

**Files:**
- `src/safecode/tools/github.py` — structural main-branch block, dry-run
- `src/safecode/agent/approvals.py` — PR preview approval step
- `src/safecode/audit/models.py` — `github_pr_created` event type
- `docs/public-contracts.md` — Section 20: GitHub PR Workflow Contract

**Tests:** `tests/test_github_pr_contract.py` (20+ tests; mock gh CLI)

---

## v6.5.x: SWE-bench Lite Compatible Harness (2 versions)

### Theme

The current live eval runs 2 self-written fixtures against a real provider.
This is a good start but cannot answer "how does this compare to other agents?"

The goal is not a high score — it is a **credible, reproducible harness** that
reads SWE-bench Lite task format and produces a structured report. The README
can then honestly state: "SWE-bench Lite compatible eval harness, N/10
instances resolved."

---

### v6.5.0 — swebench-lite-task-adapter

**What:** Adapt the existing eval runner to accept SWE-bench Lite task format.

**Key behaviors:**
- `sac eval run --suite swebench-lite --limit 10 [--task <id>]`
- Task input: SWE-bench Lite JSON (issue text, repo, base commit, test command,
  pass condition)
- Flow: checkout base commit → collect context → propose patch → apply →
  run test command → record pass/fail
- Output: `tests/snapshots/swebench_lite/report_<timestamp>.json`
- Uses mock provider by default; `--provider` flag for live run
- No claims made about score until ≥20 instances are validated

**Files:**
- `src/safecode/eval/swebench_adapter.py` — new
- `src/safecode/eval/runner.py` — extended to accept suite format
- `src/safecode/cli_eval.py` — `--suite swebench-lite` flag

**Tests:** `tests/test_eval_swebench_adapter.py` (15+ tests; synthetic tasks)

---

### v6.5.1 — swebench-lite-report-and-docs

**What:** Run 5–10 real instances (DeepSeek or Anthropic), write a structured

## Design Note: v6.2 / v6.3 Context Injection Interface

The v6.2 session memory and v6.3 semantic retrieval both inject content into
the agent context window. To avoid two independent injection paths, v6.2.0
should define a `ContextInjector` protocol that v6.3 reuses:

```python
class ContextInjector(Protocol):
    def inject(self, budget: TokenBudget) -> list[ContextBlock]: ...
```

`ContextBlock` carries a `source` tag (`memory_summary`, `project_fact`,
`semantic_result`, etc.) so the agent prompt can present them as distinct
sections. This also makes the injection auditable — each block's source is
visible in the session summary written by v6.2.0.

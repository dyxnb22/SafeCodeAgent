# v4.3.0 — Fix Watch Mode

## Summary

v4.3.0 starts the reliable test-fix loop with experimental per-task fix-loop
iteration records and `sac fix --watch`.

No stable contract changes. Patch proposals still require explicit `sac apply`;
`sac fix --watch` never auto-applies.

## Tasks

### T-4.3.0-A fix-loop-iteration-record

- `TaskIteration` gained experimental v4.3 fix-loop fields while preserving
  existing v4.1 task sidecar fields.
- `record_fix_on_task()` records append-only fix iterations with:
  `iteration_index`, `mode`, `test_command`, `suite`, `exit_code`,
  `tail_hash`, `pending_patch_id`, `pending_patch_path`, `status`, `created_at`.
- `tail_hash` is sha256 of a bounded, already-redacted failure tail.
- Raw long failure output is not stored in the task sidecar.
- Plain `sac fix` records the pending patch details when a proposal is produced.

### T-4.3.0-B fix-watch-mode

- Added `sac fix --watch [--max-iterations N] [--rerun-suite test]`.
- Default `--max-iterations` is 3.
- Default `--rerun-suite` is `test`.
- Watch mode runs one approval-gated loop step per invocation:
  `sac fix --watch` proposes a pending patch, then exits with next step
  `sac apply` followed by another `sac fix --watch`.
- Passing reruns mark the task loop state as passing/applied.
- JSON output includes `task_id`, `iteration_index`, `test_command`,
  `test_exit_code`, `pending_patch_path`, and `next_step`.
